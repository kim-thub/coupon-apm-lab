# AC07 APM 로깅 경로 진단

**진단 ID:** `2611090611d90a83`  
**상태:** COMPLETE — SYNC/ASYNC 각 3회, 전체 6회 VALID  
**실행 당시 HEAD:** `e200c914a6478b09411ac06a86ddbc0624daa9fb`  
진단 설정과 스크립트는 해당 실행에 포함된 작업 트리 변경이다. 각 run manifest의 `sourceFileSha256`가 실제 실행 파일을 식별한다.

## 조건

- 여섯 회차 모두 APM ON. `ApmTracker`의 동일한 `APM_TRANSACTION` 이벤트 본문을 SYNC와 ASYNC 경로로 출력했다.
- 순서: `SYNC → ASYNC → ASYNC → SYNC → SYNC → ASYNC`. 각 회차는 새 DB와 app 컨테이너를 사용했다.
- 사용자 100명, 초당 10명 증가, 요청 간 대기 0.1~0.3초. 워밍업 60초, 측정 60초. 측정용 쿠폰은 사용자당 614개다.
- app/DB Docker 자원과 Locust CPU/RSS를 1초마다 기록했고, JVM GC 로그와 컨테이너 로그도 보존했다.
- 기존 AC07 `110901`/`110903` 판정은 변경하지 않는다. 이 진단은 AC07 PASS/FAIL 판정이 아니다.

## 결과

| 모드 | p95 중앙값 (범위) | 성공 TPS 중앙값 (범위) | 앱 CPU 평균 중앙값 | DB CPU 평균 중앙값 | 로그 출력 지연 p95 중앙값 |
|---|---:|---:|---:|---:|---:|
| SYNC | 4.7135ms (4.4375–6.3978) | 454.57 (450.15–455.45) | 17.67% | 15.24% | 0.983ms |
| ASYNC | 4.7315ms (4.5896–5.7362) | 453.63 (449.83–456.12) | 19.07% | 15.32% | 1.027ms |

ASYNC의 p95는 SYNC보다 **0.018ms(+0.38%)** 높았고 성공 TPS는 **0.93(-0.21%)** 낮았다. 로그 출력 지연 p95도 ASYNC에서 더 낮아지지 않았다. 두 모드의 p95 범위는 겹친다.

각 회차의 APM transaction 로그 건수는 HTTP 요청 기록과 모두 일치했다. 전체 **163,185건**이 누락 없이 출력됐고 SlowTrace는 0건이었다. 앱·DB 지표는 측정 구간마다 60개씩 수집됐다. GC 로그에서 pause는 관측되지 않았다.

로그 출력 지연은 `APM startedAt + elapsedMs`부터 Docker 로그 timestamp까지의 차이다. 이 값에는 Docker 로그 수집과 timestamp 처리 시간이 포함되므로, Logback 호출 시간만 분리 측정한 값은 아니다.

앱 CPU 평균은 두 모드에서 비슷했다. 앱 최대 메모리는 회차별 약 595~608MB였다. DB 컨테이너 블록 쓰기는 회차별 20~270MB로 차이가 있었지만, 쓰기량이 낮은 ASYNC 회차도 p95 개선을 보이지 않아 원인으로 특정할 수 없다.

## 해석

이 조건에서는 **동기 APM 로그 경로가 앞선 AC07 실패의 주원인이라는 가설을 지지하지 않는다.** 비동기 경로로 바꿔도 p95가 줄지 않았고, 응답 꼬리 지연과 로그 출력 지연도 함께 움직이지 않았다.

다만 2차 AC07의 22.87ms p95는 이번 진단에서 재현되지 않았다. 당시 CPU·GC·I/O 기록도 없어 무엇이 그 두 회차의 지연을 만들었는지는 여전히 확정할 수 없다. 이번 결과는 동기 로깅을 주원인으로 보기 어렵게 하지만, 모든 실행환경에서의 영향을 완전히 배제하지는 않는다.

사용자는 이전 AC07 실험 때 별도 작업에서 CPU를 상당량 사용했고, 이를 2차 결과 이상치의 거의 확정적인 원인으로 판단한다고 밝혔다. 이 보고서에는 이를 실험자의 사후 원인 판단으로 기록한다. 당시 호스트 전체 CPU와 프로세스별 CPU 기록이 없어 독립 계측으로 입증되지는 않았다. 이번 진단도 app/DB 컨테이너와 Locust CPU만 기록했고 호스트 전체 CPU 및 다른 프로세스 지표는 수집하지 않았다.

**AC07 판정은 그대로다:** 1차 배치는 목표 PASS, 2차 배치는 유효한 목표 FAIL이며 두 배치 모두 `REVIEW_REQUIRED`다. 로깅 진단은 동기/비동기 로깅을 비교한 별도 실험이므로 기존 FAIL을 무효화하지 않는다. 재측정으로 CPU 경합 가설을 확인하려면 실험 호스트를 비우고 호스트 전체·프로세스별 CPU를 함께 기록해야 한다.
