# ADR-001: 프로젝트 범위와 구현 제약

## 상태
Accepted

## 컨텍스트
쿠폰 동시 발급과 경량 APM의 연계를 보여주는 취업용 포트폴리오를 10시간의 구현 시간 안에 완성해야 한다. 요구사항과 상세설계는 구현 전에 동결한다.

## 결정
- 프로젝트명 `coupon-apm-lab`, Java 기본 패키지 `lab.couponapm`.
- Java 21, Spring Boot, Gradle Groovy DSL, PostgreSQL(Docker), Lombok을 사용한다.
- MVP는 쿠폰 생성·단건/목록 조회·발급과 경량 APM으로 제한한다. 쿠폰 수정·삭제는 향후 개선으로 남긴다.
- 요구사항·설계·테스트 계획·WBS 문서 동결 이후부터 구현 10시간을 계산한다.
- Git 커밋은 기능 단위로 작성한다. 문서와 README는 한국어 중심으로 작성하되 기술 용어는 영어를 병용한다.
- README에 특정 상용 APM 제품명을 직접 언급하지 않는다.

## 근거
핵심 역량인 DB 동시성 제어, 실제 병목 관찰, 성능 검증에 집중하고 주변 CRUD 정책의 복잡도를 줄인다.

## 결과
구현 전 `docs/01-requirements.md`부터 `docs/07-decision-log.md`까지의 설계 문서와 테스트·증빙 계획을 완성한다. Lombok은 필요한 어노테이션만 사용하고 JPA 엔티티의 무분별한 `@Data` 사용을 피한다.

## 대안
- 수정·삭제 포함: 재고 불변식과 발급 이력 삭제 정책까지 필요하므로 제외.
- Java 패키지에 개인 이름 사용: 불필요하여 제외.
- JMeter: 프로젝트 규모와 준비 비용을 고려해 Locust 선택.

# ADR-002: 쿠폰 도메인, DB 모델 및 제약

## 상태
Accepted

## 컨텍스트
동시 발급에서도 재고 초과 발급과 중복 발급을 방지하고, DB와 애플리케이션 상태의 일관성을 유지해야 한다.

## 결정
- `coupons(id, name, total_stock, issued_count, created_at)`와 `coupon_issues(id, coupon_id, user_id, issued_at)`를 사용한다.
- `remainingStock = totalStock - issuedCount`로 계산하며 별도 DB 컬럼을 두지 않는다.
- 쿠폰 생성 시 `issuedCount = 0`; `name`은 1~100자, DB `VARCHAR(100)`.
- `total_stock >= 0`, `issued_count >= 0`, `issued_count <= total_stock`, `user_id`는 공백이 아닌 문자열이어야 하며 애플리케이션 검증과 DB `NOT NULL` 및 공백 문자열 방지 CHECK 제약으로 검증한다.
- 필수 컬럼에 `NOT NULL`, 발급 이력에 쿠폰 FK 및 `UNIQUE(coupon_id, user_id)`를 적용한다.
- 테이블별 시퀀스 `coupon_seq`, `coupon_issue_seq`를 사용한다.
- `userId`는 별도 User 엔티티 없이 공백이 아닌 `String`으로 취급하며, `coupon_issues.user_id`는 `VARCHAR(100)`으로 저장한다. 앞선 숫자형 계약은 ADR-024에 따라 변경한다.
- 시각은 `Instant`로 기록한다.

## 근거
파생 재고를 중복 저장하지 않아 정합성 부담을 줄이고, DB CHECK/UNIQUE를 마지막 안전장치로 사용한다.

## 결과
발급 이력과 발급 수량이 하나의 트랜잭션에서 일치해야 한다. DB 제약 위반과 비즈니스 오류를 구분해 처리한다.

## 대안
- `remaining_stock` 별도 저장: 동기화 대상이 늘어나 제외.
- User 엔티티: MVP 핵심에 불필요하여 제외.
- 쿠폰 유효기간 필드: 날짜 정책과 테스트가 추가되어 제외.

# ADR-003: 쿠폰 HTTP API 및 오류 계약

## 상태
Accepted

## 컨텍스트
API를 테스트 가능하게 만들기 위해 경로, 요청·응답, 오류 우선순위를 고정해야 한다.

## 결정
- `POST /api/coupons`: `{name, totalStock}` 입력, `201 Created`, `id/name/totalStock/issuedCount/remainingStock/createdAt` 반환.
- `GET /api/coupons/{couponId}` 및 `GET /api/coupons`: 단건·전체 목록 조회. 페이지네이션·검색·정렬은 MVP 제외.
- `POST /api/coupons/{couponId}/issues`: `{userId}` 입력, `201 Created`, `issueId/couponId/userId/issuedAt` 반환.
- 오류 응답은 `{code, message}` 두 필드.
- 중복 발급 `409 COUPON_ALREADY_ISSUED` / `이미 발급된 쿠폰입니다.`
- 품절 `409 COUPON_SOLD_OUT` / `쿠폰이 모두 소진되었습니다.`
- 미존재 쿠폰 `404 COUPON_NOT_FOUND` / `쿠폰을 찾을 수 없습니다.`
- `userId`가 null·빈 문자열·공백만 있는 문자열·100자 초과면 `400`; 중복과 품절이 동시에 해당하면 중복을 먼저 반환한다.
- 클라이언트가 품절을 이미 알면 요청을 막을 수 있지만, 서버는 발급 시점에 재고를 반드시 재검증한다.

## 근거
응답이 단순하고 재현 가능한 계약이며, 클라이언트 상태는 동시 요청으로 낡을 수 있다.

## 결과
Controller 검증, 예외 매핑, API 통합·스모크 테스트를 작성한다. 조회 응답의 상세 HTTP status 및 빈 목록 표현은 일반적인 성공 응답을 따르되 명세 문서에서 명시한다.

## 대안
- 중복·품절 모두 동일 메시지: 사용자 피드백이 모호하여 제외.
- 클라이언트 재고 판단만 신뢰: 경쟁 조건으로 초과 발급 가능하여 제외.

## 작성일자

# ADR-004: 발급 트랜잭션과 PostgreSQL 비관적 잠금

## 상태
Accepted

## 컨텍스트
동일 쿠폰에 동시 발급 요청이 집중되어도 정확히 재고만큼만 발급되어야 한다.

## 결정
- Service의 `issueCoupon(couponId, userId)` 단일 `@Transactional` 범위에서 모든 발급 DB 작업을 처리한다.
- 순서: 쿠폰 `PESSIMISTIC_WRITE` 조회 → 중복 검사 → 재고 검사 → `CouponIssue` INSERT → `issuedCount` 증가 → COMMIT.
- Spring Data Repository의 `@Lock`을 사용한다.
- PostgreSQL `READ_COMMITTED`를 사용한다.
- 잠금 대기 제한 목표는 3초다. 구체적 예외 매핑과 DB 설정 적용 방식은 구현 검증 시 확인한다.
- 실제 PostgreSQL row lock 대기를 별도 트랜잭션으로 재현한다. 잠금 보유 장치의 구체 구현은 아직 미결정이다.

## 근거
동일 쿠폰 행에 대한 경쟁만 직렬화하고 서로 다른 쿠폰은 독립적으로 진행할 수 있다. 실패 시 발급 기록과 카운트를 함께 롤백한다.

## 결과
동시 발급 테스트, 중복 발급 테스트, 잠금 대기·타임아웃 테스트가 필요하다. 락 보유 장치가 아직 미정이므로 관련 상세설계는 동결되지 않았다.

## 대안
- 낙관적 잠금: 이번 MVP에서는 비교 설명만 남긴다.
- Java `synchronized`: 다중 애플리케이션 인스턴스 간 동기화를 보장하지 않아 제외.
- `Thread.sleep()`으로 병목 연출: 실제 DB lock wait가 아니므로 제외.

# ADR-005: APM 추적 진입점과 활성 트랜잭션

## 상태
Accepted

## 컨텍스트
쿠폰 발급 API만 선택적으로 추적하면서 DB 대기 중인 요청의 실행 스레드를 찾아야 한다.

## 결정
- Controller 발급 메서드에 `@ApmTrace`를 붙인다.
- `HandlerInterceptor`에서 `HandlerMethod`의 어노테이션을 판별한다.
- `preHandle`에서 추적을 시작하고 `afterCompletion`에서 종료·정리한다.
- 측정 구간은 **Spring MVC Handler 처리 구간**이며 Servlet Filter 이전을 포함한 HTTP 전체 구간은 아니다.
- APM 내부 트랜잭션 ID는 UUID이며 외부 응답·헤더에 노출하지 않는다.
- `ActiveTransaction`은 transactionId, httpMethod, routePattern, startedAt(`Instant`), startNanoTime, Thread 참조, slowCaptured 상태를 가진다.
- 활성 저장소는 `ConcurrentHashMap<UUID, ActiveTransaction>`이며 요청 종료 시 즉시 제거한다.

## 근거
Interceptor는 매핑된 Controller 메서드를 알 수 있어 `@ApmTrace` 판별이 간단하다. Thread 참조는 해당 요청의 stack trace를 직접 얻는 데 필요하다.

## 결과
README와 성능 설명에 ‘HTTP 전체 latency’가 아니라 ‘Spring MVC Handler 처리 시간’을 사용한다. 예외·오류 응답 시에도 활성 엔트리 제거를 보장해야 한다. `afterCompletion` 호출 조건과 비동기 요청 처리의 범위는 구현 시 확인한다.

## 대안
- Filter + Interceptor: 더 넓은 HTTP 측정이 가능하지만 두 구성요소 사이 상태 전달이 필요해 제외.
- Controller AOP 단독: Controller 메서드 실행시간만 측정하여 제외.
- JVM 전체 thread dump: 이미 대상 Thread를 알고 있어 과도하므로 제외.

# ADR-006: Slow Transaction 감지 및 Stack Trace 수집

## 상태
Accepted

## 컨텍스트
실제 DB lock wait를 겪는 발급 요청이 왜 느린지 경량 방식으로 관찰해야 한다.

## 결정
- 전용 단일 Monitor 스케줄러 스레드가 100ms마다 활성 요청을 검사한다.
- `System.nanoTime()` 차이로 경과시간을 계산하고 500ms 이상이면 Slow로 판정한다.
- Slow 요청당 해당 Thread의 `getStackTrace()`를 한 번만 수집하며 최대 64 frame을 저장한다.
- `SlowTrace`는 transactionId, httpMethod, routePattern, startedAt, capturedAt, elapsedAtCapture, stackFrames를 포함한다.
- 설정값(500ms, 100ms, 64 frames)은 변경 가능하도록 한다.
- 현재 MVP는 Platform Thread를 사용한다. Virtual Thread는 향후 개선 항목이다.

## 근거
`Instant`는 사건 시각, `nanoTime`은 경과시간에 적합하다. 대상 스레드 직접 조회와 단일 스냅샷으로 관찰 비용을 제한한다.

## 결과
Slow 감지 로직은 주입 가능한 시간으로 경계값을 결정론적으로 테스트하고, 실제 DB lock wait를 통한 통합 검증을 별도로 수행한다.

## 대안
- 전체 JVM thread dump: 불필요한 스레드까지 수집해 비용 증가.
- 반복 stack snapshot: 정보는 늘지만 MVP 비용·복잡도 증가.
- Virtual Thread 기본 적용: 별도 동작 검증 비용 때문에 개선 과제로 보류.

# ADR-007: APM 완료 기록과 X-View 데이터 모델

## 상태
Accepted

## 컨텍스트
완료된 요청을 X-View 점으로 표현하고, 느린 점과 SlowTrace를 연결해야 한다.

## 결정
- 추적 종료 시 elapsed 계산 → 활성 Registry 제거 → `TransactionSample` 생성 → X-View 저장 및 로그 기록을 수행한다.
- `TransactionSample`은 transactionId, httpMethod, routePattern, startedAt, elapsedMs, statusCode를 가진다.
- X-View의 X축은 startedAt, Y축은 elapsedMs다.
- 실제 URI 대신 정규화된 `routePattern`을 저장한다.
- APM 조회 엔드포인트는 X-View, Active, Slow Traces의 세 종류로 구성한다.
- 메모리의 X-View 최근 보관 상한은 1,000건이며, 오래된 항목부터 제거한다. 로그는 애플리케이션이 임의 삭제하지 않는 전체 기록용으로 사용한다.
- 그래프는 JSON 데이터를 이용한 정적 scatter plot이며 웹 UI는 만들지 않는다.

## 근거
routePattern은 쿠폰 ID별 경로를 같은 API로 묶어 분석할 수 있다. 메모리는 빠른 최근 조회, 로그는 장기 증거에 적합하다.

## 결과
메모리 보관 구조·SlowTrace 별도 보관 개수·조회 API의 구체 경로와 JSON 스키마·정적 그래프 생성 방식은 **아직 미확정**이며 다음 ADR에서 결정한다. 실제 운영에서는 로그 로테이션·보관 정책이 필요하지만 MVP 구현 범위는 아니다.

## 대안
- 모든 기록을 메모리에 무제한 보관: 메모리 증가 위험으로 제외.
- GET 요청 시 조회된 기록 삭제: 반복 조회 불가능하고 GET에 부작용이 생겨 제외.
- 실제 request URI만 저장: 동일 route의 집계에 불리해 제외.

# ADR-008: 테스트 전략과 정량 성공 기준

## 상태
Accepted

## 컨텍스트
동시성 정합성, APM 탐지의 유효성, APM 부하를 객관적인 증거로 제시해야 한다.

## 결정
- Spring Service→Repository→실제 PostgreSQL 통합 테스트 중심, Controller smoke test, Locust E2E를 조합한다.
- 시간 의존 감지 로직은 fake/injected time으로 검증하고 실제 시간 기반 DB lock wait 통합 테스트를 소수 추가한다.
- Locust 기본 부하: 최대 100 users, spawn 10 users/sec, 총 60초.
- AC01: 재고 30, 동시 발급 100 → 정확히 30 성공, 초과 발급 0.
- AC02: 동일 userId의 동시 요청 20 → 정확히 1 성공, 나머지 409.
- AC03: 재고 0 → 성공 0, 409.
- AC04: 500ms 이상 요청 → SlowTrace 최소 1건.
- AC05: Slow 요청당 stack snapshot 1회, 1~64 frames.
- AC06: X-View 1,200건 기록 → 메모리 최근 1,000건, 오래된 200건 제거.
- AC07: APM OFF/ON 비교 시 p95 latency 증가 ≤15%, throughput 감소 ≤15%.
- AC08: 실제 PostgreSQL row lock wait로 SlowTrace 최소 1건 생성.
- AC09: 3초 이상 잠금 획득 실패 시 timeout, 무한 대기 금지.
- AC10: 요청 종료 후 Active Registry에 해당 트랜잭션 및 Thread 참조 잔존 금지.
- AC11: APM ON/OFF 모두 같은 쿠폰 발급 정합성 테스트 통과.
- 오버헤드 실험은 고의적 DB lock 병목 없이 warm-up 후 OFF 3회, ON 3회 수행하고 각 결과의 median을 비교한다.
- 증빙: X-View scatter plot, SlowTrace 예시, 동시성 결과, APM OFF/ON 결과, 필요 시 로그·JSON·부하 출력.

## 근거
단순 기능 동작이 아니라 정확성→실제 병목→관찰→관찰 비용까지 연결된 검증 체계가 필요하다.

## 결과
각 AC의 테스트 클래스·데이터 시딩·성공 판정 및 결과 저장 경로를 테스트 계획에 매핑한다. APM overhead 측정에서는 동일 쿠폰에 대한 과도한 경합이 APM 비용을 가리지 않도록 저경합 시나리오를 상세설계해야 한다. 15%는 프로젝트 목표이며 업계 표준 수치는 아니다.

## 대안
- 단위 테스트만 사용: 실제 PostgreSQL lock 검증 불가.
- 시간 경과 테스트만 다수 사용: 느리고 불안정할 수 있어 제외.
- 의도적 2~3초 lock wait로 APM overhead 측정: APM 비용을 가릴 수 있어 제외.

## 후속 결정 반영 (2026-11-08)
AC07 처리량의 최종 지표는 ADR-025에 따라 성공 TPS(HTTP 201 원본 및 PostgreSQL 발급 이력 검증)이며 전체 HTTP RPS는 보조 지표다.

# ADR-009: APM 메모리 보관 및 조회 API 상세 계약

## 상태
Accepted

## 컨텍스트
최근 X-View 샘플, SlowTrace, 현재 활성 요청을 빠르게 조회해야 한다. APM은 관찰 대상 서비스에 과도한 메모리·동기화 비용을 추가해서는 안 된다. 이전 결정에서 X-View 최근 1,000건과 활성 요청 종료 시 즉시 제거가 확정되었다.

## 결정
- S26: X-View는 thread-safe한 FIFO Buffer에 최근 1,000건만 저장한다. `add()`와 `getRecent()`로 접근하며, 용량 초과 시 가장 오래된 기록을 제거한다.
- S27: SlowTrace는 X-View와 분리된 thread-safe Buffer에 최근 100건을 보관한다.
- S28: `GET /api/apm/xview`는 최근 TransactionSample 배열을 오래된 순서부터 최신 순서로 반환한다.
- S29: `GET /api/apm/slow-traces`는 최근 SlowTrace 배열을 최신 순서부터 오래된 순서로 반환한다.
- S30: `GET /api/apm/active`는 조회 시점의 활성 요청 목록을 반환한다. 응답에는 transactionId, httpMethod, routePattern, startedAt, elapsedMs만 포함하고 Thread 참조를 노출하지 않는다.
- APM 조회 경로는 `/api/apm/*`로 통일한다. 조회 요청은 저장된 기록을 삭제하지 않는다.

## 근거
- X-View 1,000건은 이미 합의한 메모리 상한을 지키며, FIFO는 오래된 샘플을 자동 축출하는 정책에 직접 대응한다. 동시 요청 스레드가 기록하고 조회 스레드가 읽으므로 Buffer 자체의 동시성 제어가 필요하다.
- SlowTrace는 stack frame을 포함하여 일반 샘플보다 크므로 별도 상한 100건을 둔다. 전체 기록은 로그에 남기고 메모리는 최근 분석에 집중한다.
- X-View는 시간 축에 그리기 편하도록 오래된 순서부터, SlowTrace는 최근 장애를 먼저 살피도록 최신 순서부터 반환한다.
- Active API는 내부 Thread 객체를 외부로 노출하지 않으면서 현재 대기시간을 확인하는 데 필요한 최소 정보만 제공한다.
- `/api` 접두어 통일은 쿠폰 API와 APM API의 경로 규칙을 일관되게 만든다.

## 결과
- X-View 및 SlowTrace Buffer를 독립적인 클래스로 구현하고, 동시 접근과 용량 초과를 테스트한다.
- `getRecent()`는 읽기 전용으로 동작해야 하며 조회 시점에 안전한 목록 복사본을 반환하도록 설계한다. 정확한 동기화 구현은 코드 설계 시 선택한다.
- Active 조회 결과는 실행 중 요청이 끝나는 순간 달라질 수 있으므로 엄격한 전역 원자적 스냅샷은 요구하지 않는다.
- 세 API는 DTO만 반환하고 내부 Thread 참조·자료구조는 직렬화하지 않는다.
- 메모리에서 축출된 기록의 장기 조회는 API가 아니라 로그 분석 범위에 속한다.

## 대안
- SlowTrace도 1,000건 저장: stack frame 데이터가 커져 메모리 부담이 증가하므로 제외.
- X-View와 SlowTrace를 하나의 Buffer로 합침: 데이터 크기·보존 정책·조회 목적이 달라 제외.
- 무제한 메모리 저장: 장시간 실행 시 메모리 증가 위험으로 제외.
- GET 시 조회된 기록 삭제: 반복 조회가 불가능하고 읽기 요청에 부작용이 생겨 제외.
- Thread 참조를 API에 노출: 내부 구현 정보가 유출되고 직렬화에도 부적합하여 제외.
- `/apm/*` 별도 접두어: 다른 API와 규칙이 달라져 `/api/apm/*`로 통일.

# ADR-010: 실제 PostgreSQL Row Lock Contention 재현 방식

## 상태
Accepted

## 컨텍스트
쿠폰 발급 API의 `PESSIMISTIC_WRITE`가 실제 PostgreSQL 행 잠금 대기를 일으키는지, 그 대기를 APM이 Slow Transaction으로 감지하고 해당 요청 스레드의 Stack Trace를 수집하는지 검증해야 한다. 구현 시간은 10시간으로 제한된다.

## 결정
- **대안 A 채택:** 통합 테스트 코드에서 별도 PostgreSQL 연결과 트랜잭션을 사용하여 `SELECT ... FOR UPDATE`로 대상 쿠폰 행의 잠금을 보유한다.
- 잠금 획득 완료를 동기화 신호로 확인한 후, 실제 포트로 구동한 Spring Boot 서버에 HTTP 쿠폰 발급 요청을 전송한다.
- 요청이 잠금 대기 중일 때 APM의 SlowTrace 생성과 Stack Trace 수집을 확인한다.
- 테스트 제어 신호로 잠금을 해제한 뒤 정상 발급 결과를 검증한다. 별도 시나리오에서는 3초 잠금 대기 제한으로 인한 timeout을 검증한다.
- 잠금 보유 연결과 트랜잭션은 테스트 종료 시 반드시 정리한다.
- 수동 시연을 위한 Demo 전용 Lock API는 MVP에 추가하지 않는다.

## 근거
- 실제 PostgreSQL 행 잠금 대기를 재현하므로 단순 `Thread.sleep()`보다 검증 대상과 일치한다.
- 실제 HTTP 요청을 통과시켜 `HandlerInterceptor → Active Registry → Monitor → SlowTrace` 흐름을 함께 검증할 수 있다.
- 잠금 획득 및 해제 시점을 테스트에서 통제할 수 있어 반복 실행의 결정성이 높다.
- 실험용 API를 운영 애플리케이션에 추가하지 않아 구현·노출 범위를 줄인다.

## 결과
- 실제 PostgreSQL을 사용하는 HTTP 통합 테스트와 별도 DB 연결을 사용하는 LockHolder가 필요하다.
- 정상 대기 후 성공과 3초 lock timeout을 서로 다른 테스트 시나리오로 검증한다.
- 잠금 획득 확인, HTTP 요청 실행, SlowTrace 확인, 잠금 해제 순서를 명시적으로 동기화한다.
- PostgreSQL `lock_timeout`과 JPA 잠금 timeout 설정 중 실제 3초 제한을 적용하는 방법, 예외 매핑은 구현 전/초기 기술 확인 항목으로 남긴다.
- 별도의 Demo API는 구현하지 않으며, 기존 demo profile 사용 범위는 테스트 계획에서 재정리한다.

## 대안
- **B. Demo 전용 API에서 행 잠금 유지:** HTTP 요청만으로 수동 시연하기 쉽지만, 추가 Controller·Service와 잠금 상태·해제·중복 호출 관리가 필요해 제외한다.
- **`Thread.sleep()`으로 지연 재현:** 실제 PostgreSQL 잠금 대기가 아니므로 제외한다.
- **Service 직접 호출만으로 검증:** Interceptor를 거치지 않아 APM 전체 경로 검증에 부적합하므로 제외한다.

# ADR-011: X-View 정적 시각화 방식

## 상태
Accepted

## 컨텍스트
경량 APM이 수집한 요청별 실행시간을 시각화해 실제 PostgreSQL Lock Wait로 발생한 Slow Transaction을 포트폴리오에서 증명해야 한다. 시각화 자체의 화려함은 프로젝트 목표가 아니며 구현 시간은 10시간으로 제한된다.

## 결정
- Python + Matplotlib로 `/api/apm/xview` JSON 데이터를 읽어 정적 Scatter Plot PNG를 생성한다.
- X축은 요청 시작 시각(`startedAt`), Y축은 요청 실행시간(`elapsedMs`)으로 한다.
- 500ms Slow 기준을 표시하고 느린 요청을 구분한다.
- 생성된 PNG를 README에 실험 증거로 첨부한다.
- 실시간 대시보드나 별도 웹 프런트엔드는 MVP에 포함하지 않는다.

- 핵심은 화려한 시각화가 아니라 DB 병목을 실제 APM으로 관찰했다는 검증 가능한 증거다.
- Locust 테스트에도 Python을 사용하므로 기술 도입 비용이 작다.
- 정적 이미지는 재현 가능한 실험 결과로 보관하고 README에서 즉시 확인하기 쉽다.

## 결과
- APM JSON을 입력으로 받는 Python 시각화 스크립트와 결과 PNG가 산출물에 포함된다.
- 구체적인 스크립트 파일명, 입력 JSON 저장 경로, 출력 PNG 경로는 WBS 및 테스트 산출물 매핑에서 확정한다.
- 차트는 실험 완료 후 생성하며 라이브 갱신 기능은 없다.

## 대안
- **Chart.js 기반 HTML 그래프:** 상호작용과 꾸미기에 유리하지만 프런트엔드 개발·유지보수 범위가 늘고 MVP 목적에 불필요하여 제외한다.
- **별도 웹 대시보드:** 실시간 조회에 유리하지만 구현 시간과 복잡도가 커 제외한다.

# ADR-012: AC01~AC11 검증을 위한 테스트 계층 분리

## 상태
Accepted

## 컨텍스트
ADR-008의 AC01~AC11은 PostgreSQL 발급 정합성, APM의 시간·버퍼 처리, 실제 HTTP Lock Wait, 성능 오버헤드처럼 검증 대상이 다르다. 모든 항목을 동일한 계층에서 검증하면 실제 DB 동작을 누락하거나, 내부 상태를 확인하려고 불필요한 HTTP·테스트 전용 API를 추가하거나, 실행 시간 및 실패 원인 분석 비용이 증가할 수 있다.

본 프로젝트는 취업용 백엔드 + APM 포트폴리오이므로 테스트 통과뿐 아니라 **코드와 보고서에서 선택 이유·관찰값·한계·대안을 기술면접에서 재현 가능하게 설명**할 수 있어야 한다.

## 결정
- **추천안 A 채택: AC의 특성에 따라 테스트 계층을 분리한다.**
- Unit Test: AC04(500ms 경계값·감지 로직), AC05(요청당 Stack snapshot 1회·최대 64 frames), AC06(X-View FIFO 최근 1,000건).
- 실제 PostgreSQL Integration Test: AC01(재고 30/동시 발급 100), AC02(동일 사용자 20회 동시 발급), AC03(재고 0).
- 실제 HTTP Integration Test: AC08(별도 DB 트랜잭션이 점유한 실제 Row Lock Wait 및 APM 감지), AC09(3초 잠금 대기 제한), AC10(요청 완료 후 Active Registry 및 Thread 참조 정리), AC11(APM ON/OFF의 발급 정합성). 필요한 경우 AC01~AC03의 오류 HTTP 계약은 Controller smoke test에서 보완한다.
- Locust E2E: AC07(APM ON/OFF p95·throughput 비교). ADR-008에 따라 고의적 DB 잠금 병목을 배제하고 warm-up 후 OFF 3회·ON 3회 결과의 median을 비교한다.
- 테스트는 이미 정해진 정확한 AC 성공 기준을 따르며, 테스트 클래스명·데이터 시딩/격리·증거 파일 경로·성능 실험 세부 조건·AC09 예외 매핑은 후속 상세설계에서 결정한다.
- 최종 코드에는 검증 책임이 읽히는 테스트 이름과 검증값을 남기고, 보고서·README에는 재현 절차, 실제 관찰 결과와 검증 근거, 대안 비교, 측정 한계(예: Handler 처리 시간과 HTTP 전체 시간의 차이)를 연결한다. **실험 전 수치나 증거를 성공 결과로 기재하지 않는다.**

## 근거
- 내부 정책·시간 경계는 단위 테스트로 결정론적으로 확인할 수 있다. AC04는 실제 시간을 기다리는 방식보다 499ms/500ms 경계 검증에 적합하다.
- AC01~AC03은 Mock DB로 검증할 수 없는 PostgreSQL 트랜잭션·행 잠금·DB 제약의 정합성 검증이 필요하다.
- AC08~AC11은 실제 요청이 Controller/HandlerInterceptor를 통과해야 APM 수집, 종료 정리, ON/OFF 간섭 여부를 검증할 수 있다.
- AC07은 성능 비교라는 목적에 맞춰 Locust 결과로 p95와 throughput을 측정해야 한다.
- 실패 시 단위 로직/DB 정합성/HTTP 추적/성능 측정을 구분해 원인을 설명할 수 있어 포트폴리오 및 기술면접에서 검증 근거가 명확해진다.

## 결과
- 구현 전에 AC별 테스트 계층과 검증 책임을 테스트 계획에 매핑한다.
- PostgreSQL과 HTTP가 필요한 통합 테스트는 실제 데이터베이스 및 실제 서버 경로를 사용하고, 내부 동작 검증을 위해 MVP 밖의 Demo/테스트 전용 HTTP API를 추가하지 않는다.
- 증빙 문서에는 입력 조건·실행 절차·정확한 판정값·실제 측정 결과·실패 분석 및 한계를 기록하도록 계획한다. 코드 구현 및 실험 결과 작성은 아직 시작하지 않았다.
- 후속 결정: 테스트 데이터 격리, 증거 파일 구성, AC07 저경합 실험 상세 조건, AC09 `lock_timeout` 적용 및 예외 매핑, 10시간 WBS·설계 동결.

## 대안
- **B. 전부 실제 HTTP E2E:** 사용자 요청 경로를 일관되게 통과한다는 장점이 있다. 반면 Stack snapshot 호출 횟수·Buffer FIFO 등 내부 정책을 검증하려면 별도 관찰 지점이나 테스트 전용 장치를 추가해야 하고, 실행 비용과 실패 원인 추적 범위가 커져 제외한다.
- **C. 단위 테스트 중심:** 실행 속도가 빠르고 실패 지점이 명확하다는 장점이 있다. 반면 실제 PostgreSQL 잠금 대기와 커밋·롤백, HTTP Interceptor 추적을 증명하지 못해 프로젝트 핵심 목표에 미달하므로 제외한다.

# ADR-013: 테스트별 독립 데이터 및 트랜잭션 격리

## 상태
Accepted

## 컨텍스트
AC01~AC11은 반복 실행 시 이전 발급 이력이나 재고 상태에 영향을 받지 않아야 한다. 특히 AC01/AC02의 동시성 테스트와 AC08/AC09의 실제 HTTP + 별도 PostgreSQL LockHolder 테스트는 서로 다른 스레드·연결·트랜잭션에서 데이터를 조회하므로, 테스트 메서드 내부의 미커밋 Fixture가 보이지 않는 문제가 발생할 수 있다. 정합성을 검증하는 테스트가 데이터 초기화 문제로 실패하거나 우연히 통과하면 포트폴리오의 재현성과 기술면접 설명력이 떨어진다.

## 결정
- **대안 A 채택: 테스트 시나리오마다 독립된 쿠폰 및 사용자 데이터를 생성한다.** 각 테스트에서 초기 데이터를 커밋한 뒤 검증 대상 작업을 시작한다.
- 동시성 작업과 HTTP 요청은 테스트 메서드의 미커밋 트랜잭션에 의존하지 않는다. 발급에 필요한 쿠폰 및 사용자 식별자는 테스트 시나리오별로 격리한다.
- 테스트가 종료되면 성공·실패와 무관하게 자신이 생성한 데이터만 정리한다. 비동기/동시 작업의 종료를 확인하고 검증·증거 기록을 마친 뒤 정리한다.
- AC08/AC09의 LockHolder는 별도 DB 연결·트랜잭션에서 작동하며, 테스트 실패 또는 예외 발생 시에도 잠금 해제·롤백·연결 종료를 보장한다.
- APM ON/OFF 정합성 및 성능 비교에서는 이전 실행의 발급 상태를 재사용하지 않고, 각 실행에 동등한 초기 데이터 조건을 제공한다. AC07의 정확한 저경합 데이터 생성 규모와 초기화 절차는 별도 결정한다.
- Unit Test(시간·Stack 수집·Buffer)에는 실제 DB Fixture를 강제하지 않는다. 구체적인 Fixture 클래스·생성/정리 구현·실행 순서는 테스트 코드 상세설계 시 정한다.
- 코드와 보고서에 **격리 기준, 커밋 경계, 동시 작업 완료/정리 순서, 반복 실행 결과**를 기록하여 왜 단순 롤백만으로 실제 HTTP 동시성 테스트를 격리할 수 없는지 설명 가능하도록 한다.

## 근거
- 테스트별 전용 데이터는 AC01/AC02/AC03의 재고 및 발급 이력이 다른 시나리오에 간섭하지 않도록 한다.
- 별도 HTTP 처리 스레드 및 PostgreSQL 연결에서 커밋된 초기 데이터를 관찰할 수 있게 하므로 실제 Lock Wait 검증과 일치한다.
- 전역 초기화보다 삭제 범위를 제한할 수 있으며, 실패한 시나리오와 대상 쿠폰을 연결하여 디버깅·증거 추적하기 좋다.
- 반복 실행 가능한 테스트 Fixture, 트랜잭션 가시성, 자원 정리 정책을 코드와 기술면접에서 구체적으로 설명할 수 있다.

## 결과
- AC01~AC03 및 AC08~AC11의 사전조건은 시나리오별 고유 쿠폰·userId와 커밋된 초기 상태로 설계한다.
- 공용 DB를 통째로 지우는 전역 초기화에 의존하지 않는다. 정리 과정에서 다른 테스트의 데이터나 실험 증거를 삭제하지 않도록 한다.
- 테스트 검증값과 증거 파일 경로는 후속 AC 매핑 및 증거 산출물 결정에서 확정한다.
- 설계 확정만 수행한 상태이며, 테스트 코드 구현 및 실제 실행은 시작하지 않았다.

## 대안
- **B. 테스트 메서드 `@Transactional` + 롤백 중심:** 단일 스레드에서 수행되는 일반 통합 테스트에는 빠르고 편리하다. 그러나 별도 스레드·서버 요청·DB 연결은 테스트 메서드의 미커밋 초기 데이터를 볼 수 없고, 테스트 트랜잭션 밖에서 커밋된 변경은 해당 롤백으로 복구되지 않으므로 이번 프로젝트 전체의 기본 격리 전략으로는 제외한다. 일부 제한된 테스트에서 개별 사용 가능성은 남긴다.
- **C. 시나리오마다 DB 전체 초기화:** 테스트 간 잔여 데이터 격리를 강하게 보장하고 초기 상태를 표준화하기 쉽다. 반면 초기화 실행 비용이 크고 병렬 테스트에서 서로의 데이터를 삭제할 수 있으며 별도 준비·실행 제어가 필요해 10시간 구현 제약상 기본 전략에서 제외한다.

# ADR-014: 테스트 증거 산출물과 공개 재현성 정책

## 상태
Accepted

## 컨텍스트
본 프로젝트의 AC01~AC11 검증은 개발자 본인의 테스트 통과에 그치지 않아야 한다. 공개 GitHub 저장소에서 제3자가 동일한 검증 절차를 실행할 수 있어야 하며, 실제 측정 결과는 별도 포트폴리오 사이트의 블로그 섹션에서 설계 판단·구현·측정 근거·한계와 연결해 설명한다. 그러나 모든 AC마다 별도 JSON 자동 생성 기능을 구현하면 제한된 10시간의 구현 시간을 핵심 동시성·APM 기능이 아닌 증거 출력 도구에 소모할 수 있다.

## 결정
- **대안 A+ 채택: 핵심 증거를 선별 보관하면서 AC01~AC11 전체의 공개 재현성을 보장한다.** 선별 저장은 테스트 생략이나 비공개를 뜻하지 않는다.
- 공개 저장소에 AC01~AC11의 실행 가능한 자동 테스트 또는 재현 가능한 실험 절차, 전제조건, 기대 검증값, 실행 명령을 제공한다. 실제 PostgreSQL·HTTP Lock Wait·Locust 성능 비교에 필요한 환경 준비와 순서도 문서화한다.
- 테스트 결과 증거의 기본 경로는 `docs/evidence/`로 하고, AC별 결과 요약은 `docs/evidence/ac-results.md`에 기록한다. 각 AC를 테스트 코드 또는 실행 명령과 연결하며 테스트 조건, 기대 결과, 실제 결과, PASS/FAIL, 관련 원본 증거 및 한계를 명시한다.
- 핵심 실험의 원본 데이터와 시각화를 보존한다. 잠금 대기 증거는 `docs/evidence/lock-wait/` 아래의 `pg-wait.txt`, `slow-traces.json`, `xview.json`, `xview.png`로, 성능 비교 증거는 `docs/evidence/overhead/` 아래의 OFF 3회·ON 3회 Locust CSV와 `comparison.csv`로 계획한다. 공통 테스트 실행 결과 요약 파일 `docs/evidence/test-results.txt`도 계획한다.
- `docs/test-reproduction.md`에 JDK·PostgreSQL·Python/Locust 등 실행 환경, 데이터베이스 시작 및 테스트 명령, AC별 실행 절차, 출력 위치와 환경 차이에 따른 해석 주의를 기술한다. `README.md`에서 재현 문서·증거·핵심 보고서 및 (게시 후) 블로그 글로 연결한다.
- 증거 및 보고서에는 실행 날짜, Git 커밋, 실행 환경, 데이터 규모, 부하·APM 설정 등 재검증에 필요한 조건을 남긴다. 특히 AC07의 측정 수치는 환경에 따라 달라질 수 있으므로 동일 수치의 보장이 아닌 동일 절차와 판정식의 재현을 목표로 한다.
- 포트폴리오 블로그는 문제 정의 → 설계 선택과 대안 → 코드/재현 방법 → 관찰 결과 → 해석과 한계 → 공개 저장소 링크 흐름으로 작성한다. **포트폴리오 사이트 및 블로그 자체 구현은 이번 10시간 MVP 범위 밖**이며, 보고서·코드는 블로그에 재사용 가능한 증거와 설명을 제공한다.
- 자동 테스트가 통과하기 전에는 실제 측정값이나 PASS 결과를 만들어 적지 않는다. 원본 로그·JSON·CSV 공개 시 비밀정보와 환경별 민감정보를 제거한다.

## 근거
- 모든 AC를 공개 테스트/실험으로 재현할 수 있도록 하여 단순 스크린샷보다 검증 가능성을 높인다.
- 정책/경계/정합성 테스트는 assertion과 표준 테스트 결과를 재사용하고, 실제 Lock Wait·Stack Trace·X-View·오버헤드처럼 면접 설명에 중요한 부분의 원본 증거를 집중 보존하면 구현 비용을 통제할 수 있다.
- 저장소에서는 재현 절차와 원본 기록을, 블로그에서는 기술적 판단과 실험 결과 해석을 담당하도록 분리하면 중복 구현을 줄이고 포트폴리오 설득력을 높인다.
- 동일 실행 조건과 버전 정보를 연결하면 재실험 결과가 다를 때 환경 요인과 코드 변경을 추적할 수 있다.

## 결과
- AC01~AC11 테스트 매핑에는 테스트 계층뿐 아니라 공개 실행 방법·기대값·증거 및 보고서 참조를 포함한다.
- `docs/evidence/`와 `docs/test-reproduction.md`를 계획 산출물로 확정한다. 실제 파일은 구현·실험 단계에서 생성하며, 누락된 실제 결과를 임의로 채우지 않는다.
- X-View 스크립트 파일명, 입력/출력의 세부 CLI 계약 및 자동화 수준, 성능 비교용 저경합 데이터와 통계 계산 세부 방식은 후속 설계에서 확정한다.
- 기존 ADR-008, ADR-011~013의 테스트 성공 기준, 정적 Matplotlib 시각화, 계층 분리, 테스트별 데이터 격리는 변경하지 않는다.

## 대안
- **A. 핵심 증거 선별 저장만 규정:** 구현 비용이 낮고 필수 데이터를 모으기 쉽다. 하지만 제3자의 전체 AC 재현 절차와 포트폴리오 블로그 연결을 명시하지 않아 공개 검증 요구를 보장하기에 불충분하므로 A+로 보완한다.
- **B. AC마다 별도 JSON 결과 자동 생성:** 기계적인 집계·후처리에는 유리하고 전체 결과 포맷을 통일할 수 있다. 반면 이질적인 11개 AC별 결과 변환·직렬화·관리 코드를 추가해야 하며 자동 JSON 생성은 테스트 재현성의 필요조건이 아니므로 MVP 기본안에서 제외한다.
- **C. README 스크린샷 중심:** 제작이 간단하고 시각적으로 즉시 전달할 수 있다. 그러나 원본 조건·정확한 판정값·실제 DB 대기와 오버헤드 계산을 독립 검증하기 어렵기 때문에 단독 증거 방식으로 제외한다.

# ADR-015: AC07 저경합 성능 실험의 쿠폰 데이터 분리

## 상태
Accepted

## 컨텍스트
AC07은 APM ON/OFF 간 p95 latency 및 throughput 차이를 비교하여 APM 자체의 관찰 비용을 측정한다. 하나의 쿠폰 행에 부하를 집중하면 PostgreSQL 행 잠금 대기가 결과를 지배해 APM 비용을 구분하기 어렵다. 반면 AC01·AC08은 강한 경합과 실제 Lock Wait를 별도로 검증한다. ADR-008의 Locust 기본 부하(최대 100 users, 초당 10 users 증가, 60초), warm-up 후 OFF 3회·ON 3회, 각 모드 median 비교 및 15% 기준은 유지한다.

## 결정
- **대안 A 채택: Locust 가상 사용자별 독립 쿠폰을 사용하여 서로 다른 사용자가 동일 쿠폰 행 잠금에 경합하지 않도록 한다.** 각 사용자의 발급 요청은 실제 쿠폰 발급 API와 동일한 트랜잭션 및 APM 추적 경로를 통과한다.
- APM ON/OFF 각각에 동등한 초기 쿠폰·사용자 데이터 조건을 제공한다. 이전 실험에서 발급한 쿠폰 상태를 다음 실행에 재사용하지 않는다(ADR-013).
- 이 결정은 **저경합 데이터 분리 원칙만 확정**한다. 60초 실행 중 한 가상 사용자의 반복 발급을 어떻게 성립시킬지(쿠폰 풀/순차 발급 및 데이터 수량), 초기화 절차, warm-up 구간, 실행 순서, 부하 요청 페이싱, p95/throughput 집계식 및 결과 CSV 세부 스키마는 후속 설계로 남긴다. 재고 소진·중복 발급의 409 응답이 성능 측정을 대표하지 않도록 별도로 통제한다.
- 실험 증거에는 사용자별 쿠폰 분리와 잔여 DB/CPU/커넥션 풀 영향, 동일 조건에서의 재현 절차를 설명한다. 실제 성능 결과나 15% 달성 여부는 측정 전까지 확정하지 않는다.

## 근거
- 쿠폰별 행 잠금을 분리하면 공유 쿠폰의 Lock Wait가 APM ON/OFF 간 미세한 오버헤드를 가리는 위험을 줄인다.
- 실제 발급 HTTP 경로를 유지해 관찰 대상과 AC07 측정 대상의 일치를 보장한다.
- AC01/AC08의 강경합 실험과 AC07의 저경합 실험은 목적이 서로 다르므로, 재현 가능한 분리 설계가 보고서와 기술면접의 실험 타당성 설명에 유리하다.
- 다만 쿠폰이 달라도 커넥션 풀·CPU·DB I/O 등 공유 자원의 경합은 가능하므로 APM 이외 변수의 완전 제거라고 주장하지 않는다.

## 결과
- AC07 Locust 데이터 설계는 **가상 사용자 간 독립 쿠폰**을 기본으로 한다.
- 공개 재현 문서 및 블로그용 보고서에 강경합 정합성 검증(AC01/08)과 저경합 오버헤드 검증(AC07)의 목적 차이를 명시한다.
- 데이터 규모·반복 요청 정책과 통계·실행 순서는 다음 설계 승인 이후 확정한다. 코드 구현·부하 실험은 시작하지 않았다.

## 대안
- **B. 여러 사용자가 여러 공유 쿠폰에 분산 접근:** 준비할 쿠폰 수가 적고 실서비스의 경쟁 상황 일부를 반영한다. 그러나 사용자 분포에 따라 동일 행의 잠금 대기가 발생하고 APM 오버헤드 해석이 불명확해지므로 기본 AC07 조건에서 제외한다.
- **C. 모든 사용자가 동일 쿠폰 하나에 접근:** 데이터 준비가 단순하고 Lock Wait를 강하게 재현한다. 반면 측정값이 DB 직렬화와 재고 소진·중복 오류에 지배될 수 있어 APM 자체 비용 비교 목적에 부적합하므로 제외한다.

# ADR-016: AC07 반복 발급을 위한 사용자별 사전 생성 쿠폰 풀

## 상태
Accepted

## 컨텍스트
ADR-015에서 AC07 저경합 실험은 Locust 가상 사용자별 독립 쿠폰을 사용하기로 결정했다. 그러나 가상 사용자마다 쿠폰 하나만 배정하면 첫 발급 뒤 동일 쿠폰을 반복 발급할 때 중복·품절 409 응답이 발생해 60초 동안 정상 발급 API 성능을 측정하기 어렵다. AC07의 관심사는 쿠폰 생성이나 오류 응답의 비용이 아닌, 정상 발급 경로에서 APM ON/OFF가 미치는 영향이다.

## 결정
- **대안 A 채택: 가상 사용자별로 사전 생성한 독립 쿠폰 풀을 배정하고, 발급 요청마다 아직 발급하지 않은 다음 쿠폰을 사용한다.** 동일 쿠폰을 여러 가상 사용자가 공유하지 않는다.
- 쿠폰 및 사용자 데이터 준비는 측정 구간 밖에서 수행한다. Locust가 측정하는 요청은 `POST /api/coupons/{couponId}/issues` 발급 API로 제한한다.
- APM OFF/ON 및 각 반복 실행에 동등한 초기 데이터 조건을 준비하며, 이전 반복의 발급 이력을 재사용하지 않는다(ADR-013·015).
- 사전 생성한 쿠폰 풀이 실행 중 소진되어 409 응답 중심의 부하로 바뀌지 않도록 충분한 규모와 소진 처리 정책을 **후속 상세설계에서 확정**한다. 사전 데이터 수량, 생성·정리 방법, 가상 사용자 식별과 쿠폰 할당 방식, 요청 페이싱, warm-up, OFF/ON 실행 순서, p95·throughput 집계식은 아직 미결정이다.
- 실험 결과와 재현 문서에는 정상 발급 비율, 사용한 데이터 규모 및 조건을 명시하고, 실제 측정 전에 성능 달성 결과를 기록하지 않는다.

## 근거
- 발급 요청을 정상 성공 경로로 유지하므로 409 오류 처리비용이 p95·throughput 비교를 왜곡하는 것을 줄인다.
- 쿠폰 생성 API 호출을 측정 구간에서 제외해 발급 API 및 APM 비용 해석이 명확해진다.
- 사용자 간 행 잠금 경쟁을 제거한다는 ADR-015의 목적을 유지하며, 원본 데이터 준비 절차를 공개해 제3자 재현성과 기술면접 설명력을 높인다.
- 사전 시딩량과 준비 시간이 증가하지만, 이는 측정 구간 밖의 비용으로 분리할 수 있다. 다만 풀 소진을 방지할 수 있는 수량 산정은 후속 검토가 필요하다.

## 결과
- AC07 Locust 시나리오는 **사용자별 독립된 미발급 쿠폰을 순차 소비하는 정상 발급 요청**을 기본으로 설계한다.
- 시딩 규모·초기화·반복·통계 수집에 대한 최종 계약과 증거 파일은 후속 ADR에서 결정한다.
- 기존 ADR-008의 100 users / 10 users/sec / 60초, warm-up 후 OFF 3회·ON 3회, 15% 기준을 변경하지 않는다.
- 구현과 실험은 시작하지 않는다.

## 대안
- **B. 매 발급 요청 전 쿠폰 생성:** 쿠폰 풀 사전 준비가 덜 필요하고 항상 새로운 쿠폰을 확보할 수 있다. 그러나 생성 요청이 부하에 섞이거나 별도 생성 과정의 DB·CPU 사용이 발급 측정에 간섭하고 실험 구성이 복잡해져 제외한다.
- **C. 동일 쿠폰 재요청으로 409 오류를 포함:** 데이터 준비가 가장 단순하고 지속적인 HTTP 요청을 만들 수 있다. 그러나 대부분의 요청이 정상 발급이 아닌 중복·품절 예외 경로로 이동하여 APM overhead 평가의 대표성이 떨어지므로 제외한다.

# ADR-017: AC07 사전 측정 기반 쿠폰 풀 산정과 실험 유효성 판정

## 상태
Accepted

## 컨텍스트
ADR-015~016에서는 AC07의 가상 사용자별 독립 쿠폰 풀과 순차 발급을 확정했다. 그러나 최대 100 users, 초당 10 users 증가, 60초 실행 중 필요한 쿠폰 수는 실제 요청 처리량에 따라 달라진다. 쿠폰 풀이 소진되면 409 오류 경로가 섞여 정상 발급 경로의 APM ON/OFF 성능 비교를 왜곡한다. 공개 GitHub 재현성과 포트폴리오 기술 보고서에서 수량 산정 및 실험의 유효성을 설명할 수 있어야 한다(ADR-014).

## 결정
- **대안 B 채택 — 사전 측정 기반 데이터 산정 + 실험 유효성 검증.** 정식 측정 전에 동일한 부하 특성을 갖는 사전 측정을 수행하여 **가상 사용자별 최대 발급 요청 수**를 구하고, 여유율을 적용해 **사용자별 사전 생성 쿠폰 수량**을 정한다. 전체 쿠폰 수는 사용자별 할당량을 합산한다.
- 사전 측정의 요청 수, 최대값, 적용 여유율, 최종 수량을 기록한다. **여유율의 수치, 사전 측정 반복 횟수 및 집계 기준, 정수 올림 방식, warm-up 포함 여부, 실행 페이싱은 후속 상세설계에서 확정한다.** 실제 측정 결과 없이 임의로 고정하지 않는다.
- 정식 실험에서 **쿠폰 풀 소진 또는 예상치 못한 오류**가 관측되면 해당 실행은 **무효(INVALID)** 로 판정하고 AC07의 p95/throughput 성능 비교에 포함하지 않는다. 오류 유형과 발생 횟수, 무효 사유를 증거로 남긴다. 사전 측정과 동일한 정상 발급 경로를 비교해야 한다.
- 사전 측정 결과가 불안정하면 수량을 재산정하고, 충분한 쿠폰을 확보하기 어렵다면 해당 실험 조건 및 해석의 한계를 명시한다. **데이터 부족 상태에서 측정을 유효한 결과로 주장하지 않는다.**
- 실험 조건, 사전 측정 결과, 최종 시딩 수량, 정식 실험의 실제 결과·유효성 판정 및 한계를 **공개 GitHub의 재현 문서·증거와 포트폴리오 보고서**에 기록한다. 실제 성능 목표 달성 여부는 실험 완료 후에만 판정한다.
- ADR-008의 최대 100 users, spawn 10 users/sec, 60초 및 warm-up 후 OFF 3회·ON 3회, median 비교와 각 15% 성공 기준은 변경하지 않는다.

## 근거
- 사용자별 실제 최대 요청량을 기준으로 여유분을 확보하면 임의의 고정 수량보다 풀 소진 위험을 검증 가능하게 관리한다.
- 소진·예상 밖 오류를 명시적 무효 조건으로 삼아 정상 발급 경로와 오류 경로의 혼합이 APM 오버헤드 측정을 왜곡하는 것을 방지한다.
- 계산 근거와 원본 측정값, 무효 실행 기록까지 공개하면 제3자가 실험을 재현하고 결과의 타당성을 평가할 수 있으며 기술면접에서 설계 선택과 한계를 설명할 수 있다.
- 사전 측정이 흔들리거나 데이터 확보가 어려울 때 조건과 한계를 기록해 과도한 일반화나 근거 없는 성능 주장을 피한다.

## 결과
- AC07 테스트·보고서 설계에 **사전 측정 → 사용자별 최대 요청량 확인 → 여유율 적용 → 쿠폰 시딩 → 정식 실행 → 유효성 판정 → 비교·공개** 흐름을 포함한다.
- 정식 실험에 무효 실행이 있으면 그 실행을 OFF/ON 3회 유효 반복의 일부로 세지 않는다. 반복 충족을 위한 재실행 세부 정책은 후속 설계에서 확정한다.
- 공개 재현 문서에는 시딩 산식과 원본 수치, 유효성 판정 및 실패 사례가 연결되어야 한다. 아직 구현·측정 결과는 없다.

## 대안
- **A. 고정 크기 사전 생성:** 준비 절차가 단순하지만 처리량 변동을 반영하지 못해 소진 또는 과도한 데이터 준비 위험이 있다. 실측 기반 산정과 무효 판정 요구를 충족하기 어려워 기본안에서 제외한다.
- **C. 측정 중 쿠폰 보충:** 소진 위험을 완화할 수 있으나 생성 작업이 측정 중 DB·CPU 자원을 사용하여 APM 오버헤드 분리에 불리하고 실행 경로가 복잡해져 제외한다.

# ADR-018: AC07 쿠폰 풀 수량의 2배 여유율과 재산정 정책

## 상태
Accepted

## 컨텍스트
ADR-017은 사전 측정 기반으로 가상 사용자별 최대 요청 수를 관찰한 후 여유율을 적용해 쿠폰 풀을 생성하도록 확정했으나, 구체적인 여유율은 미정이었다. 과도한 시딩과 실험 중 쿠폰 풀 소진 위험 사이에 균형이 필요하다.

## 결정
- **대안 B 채택: 사전 측정에서 관찰한 사용자별 최대 발급 요청 수에 2.0배를 적용하여 각 사용자의 쿠폰 풀을 준비한다.** 이 결정은 여유율 100%의 기본 정책이며, 실제 요청량에 대한 검증 전 수량의 충분성을 보장하지 않는다.
- 사전 측정과 정식 실험의 조건, 사용자별 최대 요청 수, 최종 할당 수량 및 풀이 소진되었는지 여부를 기록한다(ADR-017).
- 실제 측정에서 데이터가 부족하면 해당 실행을 INVALID 처리하고 원인을 기록한 뒤, 새로운 측정값을 근거로 수량을 재산정하거나 필요시 본 결정을 변경하는 후속 ADR을 제안한다. 기존 결과를 유효하게 간주하거나 임의로 삭제하지 않는다.
- 사전 측정 반복 횟수, 사용자별 요청 수 집계 범위, 정수 올림 방식, warm-up, 요청 페이싱, ON/OFF 실행 순서, 통계 계산, 무효 실행 재실행 규칙은 **별도 일괄 승인 안건**으로 남긴다.

## 근거
- 2배 규칙은 구현·검증·공개 설명이 간단하며 관찰된 최대 요청량보다 충분한 여유를 두는 보수적 초기값이다.
- 정식 실험의 유효성 판정과 재산정 정책이 있으므로 2배 수량을 절대적인 보장으로 오인하지 않고 실제 결과로 확인할 수 있다.

## 결과
- AC07 시딩은 사용자별 사전 측정 최대값 × 2.0을 기본으로 설계한다.
- 최종 산식의 올림과 집계 단위 등 나머지 수치·실행 조건은 일괄 상세설계 승인 후 확정한다.
- 구현과 성능 측정은 시작하지 않았다.

## 대안
- **A. 1.5배:** 준비 데이터는 줄지만 요청량 증가 시 소진 위험이 상대적으로 높아 제외.
- **C. 변동성 기반 가변 여유율:** 자료 활용에 유리하지만 통계·검증·구현 부담이 커 초기 정책에서 제외.
- **2배 초과 고정 비율:** 소진 위험은 낮추나 사전 준비 비용이 커지므로 실측 부족이 확인될 때 재검토.

# ADR-019: AC07 사전 측정·실행 순서·통계·무효 판정 계약

## 상태
Accepted

## 컨텍스트
ADR-008은 AC07의 부하 조건(최대 100 users, spawn 10 users/sec, 60초), 정식 OFF 3회·ON 3회와 중앙값 비교 및 p95·throughput 각각 15% 목표를 확정했다. ADR-015~018은 사용자별 독립 쿠폰 풀의 순차 발급, 사전 측정 기반 수량 산정, 풀 소진 시 무효 처리 및 최대 관측 요청량의 2배 여유율을 확정했다. 재현 가능한 실행 절차·통계 모집단·실험 편향 통제가 필요하다.

## 결정
- **사전 측정 대안 C 채택:** 정식 실험과 동일한 100 users, 초당 10 users 증가, 60초 조건으로 APM OFF **3회**, ON **3회** 사전 측정한다. 사전 측정은 수량 산정용이며 정식 성능 비교에 포함하지 않는다. 각 사전 실행에는 충분한 임시 쿠폰 풀이 필요하며 소진 시 해당 실행을 무효 처리하고 풀 확대 후 다시 측정한다.
- **요청량 집계 대안 B 채택:** 유효한 사전 측정 6회에서 **개별 가상 사용자별로 관측한 정상 발급 요청 수** 중 전역 최댓값 `M`을 구한다. 모든 사용자에게 같은 수의 쿠폰 `ceil(2.0 × M)`개를 배정하고, 100명 기준 총 필요량은 `100 × ceil(2.0 × M)`개로 계산한다. 2배 여유율은 ADR-018을 따른다. 사용자 식별 및 요청 수는 재현 가능한 Locust 측정 기록으로 집계한다. 부하 ramp-up에 따른 사용자별 실행시간 차이도 함께 기록한다.
- **Warm-up·순서 대안 B 채택(ADR-023에 따라 2026-11-08 개정):** 사전 측정 **6회와 정식 측정 6회 각각** 독립된 Spring Boot 서버 시작(동일 이미지·동일 JVM 설정) → APM 모드 및 준비 상태 검증 → **60초 Warm-up → 60초 측정** 절차를 적용한다. Warm-up과 측정에는 서로 다른 쿠폰 풀을 사용하며 사전 검증 요청 또한 별도 쿠폰으로 수행한다. Warm-up 요청·성능 수치는 사전 요청량 집계나 정식 성능 비교에 포함하지 않는다. 정식 측정 순서 **OFF → ON → ON → OFF → OFF → ON**은 유지한다. 사전 측정 순서 및 각 실행의 조건은 실행 Manifest에 기록하고, 모든 실행에서 같은 재시작·예열·측정 계약을 적용한다. PostgreSQL은 서버 재시작 간 동일 설정과 데이터 볼륨을 유지하며 DB 캐시·WAL·누적 데이터로 인한 잔여 편향은 결과 해석 시 명시한다.
- **요청 페이싱 대안 B 채택:** Locust 사용자는 발급 응답을 받은 뒤 **0.1~0.3초 무작위 대기**하고 사용자별 미발급 쿠폰을 순차 소비한다. OFF/ON에서 동일한 규칙을 적용한다. 이는 정해진 closed-loop 사용자 부하 아래의 비교이며 서버의 이론적 최대 처리량 테스트로 해석하지 않는다.
- **통계 대안 B 채택:** 각 유효한 정식 60초 실행의 **성공(201) 발급 요청만** 대상으로 p95 응답 지연시간과 성공 처리량 `TPS = 정상 커밋 검증된 HTTP 201 발급 요청 수 / 60초`를 계산한다. 각 모드의 실행별 p95 3개와 성공 TPS 3개의 **중앙값**을 각각 산출한다. `p95 증가율 = (ON p95 중앙값 / OFF p95 중앙값 - 1) × 100`, `throughput 감소율 = (1 - ON TPS 중앙값 / OFF TPS 중앙값) × 100`. 두 값이 각각 **15% 이하**일 때에만 ADR-008의 AC07 수치 목표 통과로 판정한다. 이는 지정된 HTTP/Locust 측정 기준이며 ADR-005의 APM 내부 Handler 처리시간과 혼동하지 않는다.
- **유효성 및 재실행:** 쿠폰 풀 소진, 예상하지 못한 HTTP 오류, Locust 실행 실패, 부하 조건 불일치, DB 연결 장애 등 실험 환경 문제가 확인된 실행은 **INVALID**로 표시하고 중앙값 계산에서 제외한다. 원인·횟수·원본 기록을 보존한 뒤 원인을 해소하고 같은 모드·조건으로 재실행하여 OFF/ON 각각 **유효한 3회**를 확보한다. 무효 실행을 조용히 삭제하거나 유효한 실행으로 계산하지 않는다. 결과가 불안정하거나 필요한 데이터를 확보하지 못하면 한계 또는 AC07 미판정을 명시한다.
- **공개 증빙:** 재현 명령과 환경(JDK/DB/Locust 버전 및 리소스 설정), 시딩 방법, 사전 6회의 사용자별 요청 수 및 최댓값 `M`, 계산된 쿠폰 풀 크기, Warm-up·정식 실행 순서, 실행별 p95·성공 TPS·전체 HTTP RPS·성공/실패 건수, INVALID 사유, 중앙값·15% 판정, Git 커밋과 측정 날짜를 GitHub 문서 및 포트폴리오 보고서에 기록한다. 실제 값은 실험 후 입력한다.

## 근거
- **사전 측정 3회씩:** 1회보다 우연한 실행 상태에 덜 의존하고 2회보다 사용자별 최대 요청량 추정에 관측 기회를 추가한다. 다만 3회만으로 수량 충분성이나 통계적 유의성이 보장되지는 않으므로 풀 소진 검증을 별도로 유지한다.
- **전역 최대 요청량 × 2:** 빠른 사용자도 동일한 쿠폰 할당량 내에서 정상 발급을 계속할 여지를 확보한다. 사용자별 가변 할당보다 시딩과 공개 재현이 단순하다. 처리량이 달라질 수 있으므로 사전 측정과 무효 판정을 결합한다.
- **교차 실행과 실행별 Warm-up:** 모드별 일괄 측정보다 시간 경과·캐시·온도 등 순서 영향의 한 방향 쏠림을 완화하고, 각 실행의 JVM 시작·예열 조건을 통일하여 모드별 상태 차이를 줄인다. DB 내부 캐시와 호스트 환경까지 완전히 동일해진다고 주장하지 않는다(ADR-023).
- **0.1~0.3초 대기:** 발급 API만 반복 호출하면서 부하를 지속하고 응답 완료 후 다음 요청을 보내는 조건을 양쪽 모드에 동일하게 적용한다. 최대 처리량 평가와 구분한다.
- **실행별 중앙값·무효 조건:** 개별 실험의 분산과 이상을 볼 수 있고 기존 ADR-008과 일치한다. 정상 발급만 통계에 넣되 오류가 있는 실행 자체를 무효로 해 성공 요청만 선별하여 문제를 은폐하지 않는다. 공개된 원본과 유효성 판단이 기술면접과 제3자 검증에 적합하다.

## 결과
- AC07의 Locust 사전 측정 **OFF 3회 + ON 3회**, 정식 실행 **OFF 3회 + ON 3회**에 **매 실행 직전 독립 서버 시작 및 60초 Warm-up**을 적용한다(총 12개 실행 단위). 지정된 정식 실행 순서·집계·재실행 규칙은 유지하며, 이 Warm-up 정책은 ADR-023 채택으로 기존 모드별 각 1회에서 개정되었다.
- 다음 설계에서 구체적인 Locust 사용자 식별 방식, 초기 시딩 자동화, 통계 추출/검증 스크립트와 실행 명령을 확정한다. 구현·측정은 아직 시작하지 않았다.
- 성능 수치 및 결과는 사후 관측값으로만 기록하고, 반복 3회·15% 목표를 업계 일반 성능 보증이나 통계적 유의성으로 과장하지 않는다.

## 대안
- **사전 측정 A(각 1회):** 빠르지만 우연한 처리량 저하 시 필요한 풀을 과소 추정할 가능성이 높아 제외.
- **사전 측정 B(각 2회):** 준비 비용과 신뢰성의 절충이지만 관측 기회를 늘리려는 사용자 요청으로 **C(각 3회)** 채택.
- **요청량 평균 / 사용자별 개별 할당:** 평균은 빠른 사용자 풀 소진을 감추며, 사용자별 할당은 매핑·시딩 복잡도가 증가해 제외.
- **OFF 3회 후 ON 3회 / 완전 무작위 순서:** 전자는 시간 편향이 한쪽에 집중될 수 있고, 후자는 재현 절차 복잡도가 커 고정 교차 순서 채택.
- **무대기 최대 부하 / 고정 RPS 주입:** 전자는 병목과 불안정성이 커질 수 있고, 후자는 관측 throughput 차이를 요청률 상한이 가릴 수 있어 지정 대기 범위 채택.
- **요청 통합 통계 / 실행 평균:** 전자는 실행 간 편차를 숨기고 후자는 이상 실행에 민감해 실행별 중앙값 채택.

## 기술면접·보고서 설명 근거
1. **왜 AC07에서 DB Lock 경합을 줄였나?** 관찰 대상인 APM 자체의 비용을 DB 행 잠금 대기라는 큰 외생 변수와 구분하기 위해서다. 높은 경합의 정합성과 Lock Wait는 AC01·AC08에서 별도 검증하므로 검증 공백을 만들지 않는다. 저경합이 곧 무경합이나 완벽한 성능 분리를 뜻하지는 않는다.
2. **왜 고정 수량 대신 사전 측정으로 쿠폰 풀을 산정했나?** 60초 동안의 실제 발급 요청 수는 응답시간·사용자 ramp-up·실험 환경에 따라 달라진다. 사전 실행의 사용자별 최대 요청 수 `M`과 2배 여유율을 기록하면 데이터 규모의 산정 근거를 검증할 수 있다. 부족하면 해당 실행을 무효화하고 재산정한다.
3. **왜 OFF/ON 교차 실행인가?** 한 모드를 먼저 몰아서 실행하면 시간에 따른 부하·캐시·온도 변화가 모드 효과처럼 보일 수 있다. 고정된 교차 순서는 그런 편향을 완화하면서 재현하기 쉽다. 다만 환경 drift를 완전히 제거하지는 못한다.
4. **왜 평균보다 중앙값을 사용하는가?** 유효 실행 3회 중 한 번의 일시적 변동이 평균을 크게 바꾸는 위험을 줄이며 ADR-008의 기존 계약을 따른다. 각 회차 수치도 공개해 중앙값이 실행 간 변동성을 숨기지 않도록 한다. 3회만으로 통계적 유의성을 증명하지 않는다.
5. **실험이 유효하지 않을 때 어떻게 판정·재현하는가?** 풀 소진·예상 밖 오류·부하 조건 이탈·환경 장애를 사전에 INVALID 조건으로 정하고 원본과 사유를 보존한다. 원인을 수정한 뒤 같은 모드·조건에서 다시 실행하며 OFF/ON 각각 유효 3회를 확보할 때만 비교한다. 제약이 해소되지 않으면 결과의 한계를 기록한다.

## 개정 이력
- 2026-11-08: ADR-023 승인에 따라 모드별 각 1회 Warm-up을 사전·정식 **각 실행 직전 60초 Warm-up**으로 개정. 실행 순서, 부하 조건, 통계 및 유효성 계약은 유지.

## 후속 결정 반영 (2026-11-08)
ADR-025에 따라 기존 성공 RPS 표현을 성공 TPS로 개정하고 요청별 원본·DB 커밋 대조·60초 경계·Nearest-Rank 계산 계약을 적용한다. 실행별 독립 DB 및 사전/Warm-up 사용자당 601개도 ADR-025를 따른다.

# ADR-020: PostgreSQL 행 잠금 대기 3초 제한 및 HTTP 오류 응답 정책

## 상태
Accepted

## 컨텍스트
쿠폰 발급은 Spring Data JPA의 비관적 쓰기 잠금(`PESSIMISTIC_WRITE`)을 통해 쿠폰 행을 잠근 후 중복 발급 및 재고를 검사한다(ADR-004). 다른 트랜잭션이 잠금을 오래 보유하면 발급 요청이 DB 잠금 획득을 기다리므로, 잠금 대기 3초 제한과 HTTP 오류 계약을 명시해야 한다. 기존 중복 발급 및 재고 소진의 HTTP 409와 일시적 잠금 획득 실패를 구별하고, 실제 PostgreSQL 통합 테스트로 검증해야 한다.

## 결정
- **잠금 제한 방식 A 채택:** 쿠폰 발급 트랜잭션 내부에서 비관적 잠금 조회 전에 `SET LOCAL lock_timeout = '3s'`를 실행한다. 설정과 잠금 조회가 동일한 PostgreSQL 트랜잭션에 속하도록 구성한다. `SET LOCAL`은 해당 트랜잭션에만 유효하며, 3초는 DB의 잠금 획득 대기 제한이지 전체 HTTP 응답시간 제한이 아니다.
- **HTTP 응답 방식 B 채택:** 해당 발급 경로의 PostgreSQL 잠금 획득 시간 초과는 HTTP **503 Service Unavailable**과 오류 코드 **`COUPON_LOCK_TIMEOUT`**으로 응답한다. 중복 발급·재고 소진은 기존 HTTP 409를 유지한다. 자동 재시도는 MVP 범위에서 제외한다.
- **예외 식별:** PostgreSQL SQLSTATE `55P03` 및 해당 SQL이 실행된 잠금 대기 경로를 함께 확인한다. Spring Data JPA/Hibernate/JDBC의 실제 예외 래핑은 실행 환경의 통합 테스트로 확인하고, 확인된 잠금 획득 실패만 애플리케이션 `CouponLockTimeoutException`으로 변환하여 `@RestControllerAdvice`에서 503으로 매핑한다. `55P03`만으로 정확히 3초가 지났다고 단정하지 않으며, 광범위한 잠금 관련 예외를 모두 503으로 매핑하지 않는다.
- **검증:** 실제 PostgreSQL에서 잠금 미경합 시 정상 발급, 약 1초 대기 후 잠금 해제 시 정상 발급, 3초 초과 잠금 보유 시 503과 `COUPON_LOCK_TIMEOUT`, 발급 이력 및 발급 수량 불변, 요청 완료 후 APM Active Registry 정리, SlowTrace 기록을 검증한다. 관측 대기시간·SQLSTATE·HTTP 결과를 증거에 남긴다.
- **증거:** ADR-014의 `docs/evidence/lock-wait/` 및 `docs/evidence/ac-results.md`에 테스트 조건·결과·원본 증거를 기록한다. 실제 구현·검증 전에는 예상 동작을 관측 결과로 표기하지 않는다.

## 근거
- PostgreSQL을 이미 채택했고 실제 행 잠금 대기 검증이 프로젝트 목적이므로 DB가 직접 잠금 대기시간을 제한하는 방식이 명확하다.
- 트랜잭션 한정 설정은 커넥션 풀의 다른 트랜잭션에 제한이 의도치 않게 전파되는 위험을 줄인다.
- HTTP 503은 일시적인 잠금 경합을 비즈니스 상태 충돌(409)과 구별한다. 단, 자동 재시도는 경합을 증폭할 수 있어 제외한다.
- SQLSTATE와 실행 경로를 함께 확인하여 예외의 과도한 일반화를 피하고, 실제 ORM 예외 변환을 테스트로 입증한다.

## 결과
- 잠금 제한 구현과 오류 응답의 상세설계 계약이 확정되었다. 실제 트랜잭션 경계·예외 래핑·시간 측정은 PostgreSQL 통합 테스트로 검증한다.
- 잠금 대기 제한은 요청 전체의 3초 SLA가 아니며, DB 외 처리시간과 HTTP 응답 전송시간은 별도다.
- 자동 재시도는 구현하지 않는다.

## 대안
- **잠금 적용 B — JPA `jakarta.persistence.lock.timeout` 힌트:** 선언적이고 간단하지만 Hibernate 버전과 PostgreSQL Dialect에 따라 실제 3초 대기 제한 적용이 달라질 수 있어 제외.
- **잠금 적용 C — Java 타이머/Future 취소:** 애플리케이션 측 시간 관리는 가능하나 스레드 취소가 DB 잠금 대기 중단·트랜잭션 롤백을 보장하지 않으며 구현 복잡도가 커 제외.
- **응답 A — HTTP 409:** 기존 발급 실패와 형식상 일관적이나 일시적인 서버 자원 경합을 중복·재고 충돌과 혼동할 수 있어 제외.
- **응답 C — HTTP 500:** 구현은 단순하지만 예상 가능한 잠금 획득 실패를 일반 서버 오류와 구분하지 못해 제외.

## 기술면접·보고서 설명 근거
1. **왜 Java 타이머 대신 PostgreSQL인가?** Java 작업 취소가 실제 DB 잠금 대기를 즉시 종료한다는 보장이 없어, DB가 직접 잠금 대기 제한을 집행하도록 했다.
2. **왜 JPA Lock Timeout Hint가 아닌가?** 코드상 힌트와 실제 PostgreSQL 3초 동작은 같다고 보장할 수 없어 구현체 의존성을 줄이는 명시적 DB 설정을 택했다.
3. **왜 `SET LOCAL`인가?** 동일 트랜잭션에만 적용되는 설정으로 커넥션 재사용 시 다른 트랜잭션에 설정이 남지 않게 하기 위해서다.
4. **왜 HTTP 503인가?** 재고 소진·중복 발급과 일시적인 잠금 획득 실패를 구별하기 위해서다. 자동 재시도는 구현하지 않는다.
5. **왜 SQLSTATE를 확인하는가?** Spring/Hibernate 예외 클래스가 여러 DB 원인을 포괄할 수 있으므로 DB 오류 코드와 발생 경로를 함께 검증하기 위해서다.

# ADR-021: X-View 시각화 스크립트의 실행 및 입출력 계약

## 상태
Accepted

## 컨텍스트
ADR-011은 Python·Matplotlib으로 요청 시작 시각(X축)과 실행시간 밀리초(Y축)의 산점도를 정적 PNG로 생성하도록 결정했다. ADR-014는 실제 잠금 대기 실험의 JSON과 PNG를 GitHub에 증거로 보존하도록 정했다. 동일한 원본 데이터로 서버 없이 시각화를 재생성하고, 잘못된 입력을 증거로 사용하지 않도록 스크립트 실행 및 입출력 계약을 확정한다.

## 결정
- **실행 방식 B:** 독립 CLI 스크립트 `scripts/plot_xview.py`를 Python으로 작성한다. Java 애플리케이션 실행과 분리한다.
- **입력 방식 B:** 실행 중인 API나 DB에 직접 연결하지 않고 저장된 JSON 파일을 `--input` 인자로 받는다.
- **데이터 구조 B:** 최상위 객체에 `metadata`와 `transactions` 배열을 둔다. `metadata`에는 필수 필드 `experiment`(실험 식별자), `apmEnabled`(불리언), `capturedAt`(타임존을 포함한 수집 시각)을 둔다. 각 요청에는 `id`(식별자), `startedAt`(타임존 포함 시작 시각), `elapsedMs`(0 이상의 실행시간 밀리초)를 필수로 둔다. API 응답 DTO와 증거 JSON 형식이 일치하도록 구현 시 확인하며, 기존 확정 계약과 충돌하면 임의로 변경하지 않고 재검토한다.
- **출력 방식 B:** `--output` 인자로 PNG 저장 경로를 명시한다. 상위 디렉터리가 없으면 생성하며 같은 파일이 존재하면 덮어쓴다.
- **오류 처리 B:** 입력 파일 부재, JSON 구문 오류, 필수 필드 누락, 시간 형식 오류, 음수 실행시간, 빈 `transactions` 배열, 출력 실패 시 오류를 명확히 표시하고 비정상 종료한다. 오류 입력으로 유효한 PNG가 생성된 것처럼 취급하지 않는다.
- **대표 실행 명령:** `python scripts/plot_xview.py --input docs/evidence/lock-wait/xview.json --output docs/evidence/lock-wait/xview.png`.
- **증거 및 재현:** JSON 원본, 생성된 PNG, 실행 명령, Python·Matplotlib 버전과 실험 조건을 공개한다. 동일한 입력으로 같은 시각적 의미의 그래프를 재생성할 수 있으나 실행 환경에 따라 PNG 바이너리 동일성은 보장하지 않는다.

## 근거
- 독립 CLI와 저장된 JSON을 사용하면 APM 서버·PostgreSQL 없이도 제3자가 시각화 증거를 재현할 수 있다.
- 메타데이터와 요청 배열을 함께 보존하면 그래프가 어떤 실험에서 생성됐는지 추적할 수 있다.
- 출력 경로를 명시하면 여러 실험의 산출물을 구분하고 README에 재현 명령을 그대로 기록할 수 있다.
- 잘못된 데이터에서 실패하도록 하여 누락·왜곡된 그래프가 정상 증거로 오해되는 위험을 줄인다.

## 결과
- Python·Matplotlib 설치 및 JSON 계약 관리가 필요하다.
- 시각화는 Java 애플리케이션의 핵심 발급·계측 경로와 분리된다.
- API DTO와 증거 JSON의 구조적 정합성은 구현 및 재현 테스트에서 검증한다. 아직 실제 측정 데이터나 PNG 생성 성공을 주장하지 않는다.

## 대안
- **실행 A — Java 실행 중 자동 생성:** 자동화는 가능하지만 발급 서버와 시각화 책임이 결합되어 제외.
- **실행 C — Jupyter Notebook:** 탐색 분석에는 유리하지만 셀 실행 순서와 상태 의존성이 있어 재현용 기본 경로에서 제외.
- **입력 A — APM API 직접 호출:** 최신 데이터 조회는 쉽지만 재현에 서버 실행이 필요해 제외.
- **입력 C — PostgreSQL 직접 조회:** DB 연결·스키마 의존성을 추가해 제외.
- **데이터 A — 단순 배열:** 파싱은 쉽지만 실험 메타데이터 보존이 불편해 제외.
- **데이터 C — CSV:** 분석 도구와 호환되지만 APM JSON API와 별도 변환이 필요해 제외.
- **출력 A — 고정 경로:** 간단하지만 다른 실험 결과를 덮어쓸 수 있어 제외.
- **출력 C — 실행 시각 기반 자동 파일명:** 덮어쓰기는 방지하지만 재현할 때마다 파일명이 달라져 제외.
- **오류 A — 잘못된 레코드 무시:** 누락 사실을 놓칠 수 있어 제외.
- **오류 C — 경고 후 부분 그래프 생성:** 불완전한 결과가 정상 증거로 사용될 수 있어 제외.

## 기술면접·보고서 설명 근거
1. **왜 Java 대신 Python인가?** Java는 발급 및 APM 계측에 집중시키고, 시각화는 독립된 분석 도구로 분리하기 위해서다.
2. **왜 API 직접 호출 대신 JSON 파일인가?** 서버 실행 없이 원본 증거만으로 그래프를 재현할 수 있도록 하기 위해서다.
3. **왜 메타데이터 포함 JSON인가?** 요청별 측정값과 실험 식별·수집 조건을 함께 보존하기 위해서다.
4. **왜 출력 경로를 인자로 받는가?** 실험별 산출물을 분리하고 동일한 재현 명령을 공개하기 위해서다.
5. **왜 잘못된 입력에서 실패하는가?** 데이터 일부가 누락된 그래프를 정상적인 실험 증거로 오해하지 않도록 하기 위해서다.

# ADR-022: 공개 재현을 위한 테스트 데이터 준비 및 실험 실행 자동화

## 상태
Accepted

## 컨텍스트
공개 GitHub 저장소를 복제한 제3자가 동시성 정합성, PostgreSQL 실제 잠금 대기, APM ON/OFF 오버헤드를 재현하려면 실행별 데이터 격리, Locust 가상 사용자별 쿠폰 할당, 안전한 정리, 통일된 실행 명령, 원본 증거와 결과 계산의 연결이 필요하다. ADR-013~019의 기존 실험 조건을 유지한다. 구현 시간 절약 자체보다 재현성·검증 가능성·포트폴리오 설명력을 우선하되 불필요한 범용 플랫폼 구축은 피한다.

## 결정
1. **실행 식별 — runId + Manifest:** 매 실행에 고유 `runId`를 부여하고 쿠폰 이름·문자열 `userId`에 실행 네임스페이스를 사용한다. PostgreSQL이 발급하는 실제 쿠폰 기본키와 실행 식별자는 구분한다. Manifest JSON에 실행 조건, 생성 수량, 쿠폰 ID 매핑 및 데이터 소유 범위를 기록한다.
2. **가상 사용자 할당 — 일괄 시딩 + 전용 할당 큐:** 성능 측정 시작 전에 테스트 전용 스크립트로 PostgreSQL에 쿠폰을 일괄 삽입한다. 스키마 제약조건을 준수하고 수량·초기 발급 상태를 검증한다. 사용자별 중복 없는 쿠폰 ID 목록을 만들고 Locust 단일 프로세스 내 전용 큐에서 가상 사용자당 하나의 묶음만 배정한다. 목록을 순차 소비하며 소진, 중복 할당, 실제 사용자 수 불일치 시 실행을 INVALID로 판정한다. 다중 워커는 기본 재현 범위에서 제외하고 확장 시 별도 분산 할당 설계가 필요하다.
3. **초기화·정리 — 실행별 신규 데이터 + 명시적 소유 범위 정리:** 사전 측정·Warm-up·정식 측정 각 실행마다 독립 쿠폰 풀을 생성하고 기존 발급 상태를 복구해 재사용하지 않는다. 실행 결과·Manifest·증거를 먼저 보존한다. 정리는 자동 실행 종료 단계에 포함하지 않으며 `make clean-run RUN_ID=...`와 같이 명시적으로 요청했을 때 해당 실행 소유 데이터만 대상으로 한다. 삭제 전 runId 유효성·대상 범위를 검증하고 외래키에 맞춰 발급 이력부터 정리한다. 전체 테이블 TRUNCATE 및 무조건적 전체 삭제는 금지한다.
4. **실행 자동화 — Makefile + 역할별 스크립트:** Makefile을 공개 실행 진입점으로 두고 `make test-unit`, `make test-integration`, `make test-lock-wait`, `make test-overhead`, `make evidence`, `make clean-run RUN_ID=...` 명령을 제공한다. 환경 확인, 데이터 시딩, Locust 실행, 결과 분석 및 검증은 전용 스크립트로 분리한다. 기본 공개 실행 환경은 Linux/WSL2를 기준으로 문서화한다. APM OFF/ON 전환·실제 활성 상태 검증·서버 준비 상태 확인의 구체적인 계약은 ADR-023에서 확정한다. 이 명령들은 설계 계약이며 구현 전에는 실행 가능하다고 주장하지 않는다.
5. **증거 수집 — 원본 CSV + Manifest + 자동 검증 보고서:** Locust 원본 CSV·로그와 별도 사용자별 요청 수 및 쿠폰 소진 기록을 보존한다. Manifest에 runId, APM 활성 상태, 실행 시간, 사용자 수, 증가 속도, 쿠폰 수량, Git 커밋·도구 버전 등 재현 조건을 남긴다. 분석 스크립트가 HTTP 201 성공 수, 예상 밖 오류, 정상 발급 p95, 성공 TPS, 전체 HTTP RPS, DB 커밋 검증, 쿠폰 소진, VALID/INVALID, OFF/ON 중앙값 비교를 산출한다. 원본과 Manifest의 runId 일치 여부를 검증한다. 무효 실행도 원본과 원인을 보존하고 유효한 실행으로 대체하여 비교한다.

## 근거
- `runId`에 Manifest를 결합하면 실행 구분뿐 아니라 준비한 데이터와 측정 조건의 실제 일치 여부를 추적할 수 있다.
- 사전 일괄 시딩은 측정 구간에서 쿠폰 생성 부하를 제거하고 준비 시간을 줄이며, 전용 큐는 사용자별 데이터 중복 할당을 방지한다.
- 실패 직후 자동 삭제하지 않으면 원인 분석에 필요한 DB 상태와 증거를 보존할 수 있고, 명시적 범위 지정 정리는 다른 테스트 데이터 손상을 방지한다.
- Makefile은 간결한 실행 진입점을 제공하고 복잡한 흐름은 전용 스크립트에 위임하여 책임을 분리한다.
- 원본·메타데이터·자동 계산 결과를 연결하면 포트폴리오의 수치를 제3자가 재검산할 수 있다.

## Trade-off 및 보완 대안
- **runId 단독:** 파일 관리 비용은 적지만 생성 ID·실험 조건 추적이 부족하다. Manifest를 추가하여 보완한다. **별도 실행 관리 DB 테이블:** 소유권 관리에 유리하지만 스키마·관리 로직이 증가하여 제외한다.
- **가상 사용자에게 쿠폰 임의 할당:** 구현은 간단하지만 중복 가능성이 있다. 단일 프로세스 전용 큐로 보완한다. **Redis 등 분산 할당:** 다중 워커에 유리하지만 별도 인프라 비용 때문에 현재 범위에서 제외한다.
- **쿠폰 생성 API를 반복 호출:** 준비 경로가 단순하지만 대량 데이터 생성 시간이 길고 측정과 준비 경로가 혼재될 수 있다. 측정 전 DB 일괄 시딩으로 보완하되 스키마 제약 및 초기 상태를 검증한다.
- **실행 종료 즉시 자동 삭제:** DB 누적을 줄이지만 실패 분석 자료를 잃을 수 있다. 증거 수집 후 명시적 정리로 보완한다. **매 실행 DB 전체 재생성:** 초기화는 명확하지만 다른 데이터 손상 위험과 인프라 비용이 있어 제외한다.
- **Makefile 단독:** 실행 명령은 통일되지만 오류 처리와 단계별 상태 검증이 복잡해진다. 전용 스크립트를 결합한다. **범용 Python 오케스트레이터:** 유연하지만 과도한 범용화는 피한다.
- **원본 CSV만 보존:** 측정값은 남지만 사용자별 소진·실험 조건·계산 근거가 부족하다. Manifest와 검증 보고서로 보완한다. **시계열 DB·대시보드:** 분석 확장에는 유리하나 현재 목표에 필수적이지 않아 제외한다.

## 결과
- 테스트 전용 시딩·Manifest·사용자 할당·실행 제어·결과 검증 코드가 추가된다. 구현량 증가 자체를 회피하는 것보다 실험의 재현성·증거 품질을 우선한다.
- 데이터 정리는 자동이 아닌 명시적 작업이므로 실행 데이터가 누적될 수 있다. 소유 범위 확인과 안전한 정리 명령으로 관리한다.
- 기본 성능 실험은 Locust 단일 프로세스에 한정된다. 다중 워커 결과를 같은 계약으로 재현할 수 있다고 주장하지 않는다.
- APM 전환과 서버 상태 확인의 구체적 방식은 ADR-023에서 확정했다. 코드 구현과 10시간 타이머는 아직 시작하지 않는다.

## 기술면접·보고서 설명 근거
1. **왜 Manifest인가?** 실행 데이터의 출처와 실제 준비 수량, 실행 조건을 연결해 검증하기 위해서다.
2. **왜 일괄 시딩과 전용 큐인가?** 측정 외 부하를 제거하고 사용자별 쿠폰 중복 할당을 방지하기 위해서다.
3. **왜 자동 삭제하지 않는가?** 실패 원인 분석에 필요한 증거를 보존하고 삭제 범위를 통제하기 위해서다.
4. **왜 Makefile과 스크립트를 결합하는가?** 공개 진입점의 단순함과 실행 흐름의 검증·오류 처리를 분리하기 위해서다.
5. **왜 원본과 보고서를 함께 보존하는가?** p95·성공 TPS·유효성 판단을 제3자가 재계산할 수 있도록 하기 위해서다.

## 후속 결정 반영 (2026-11-08)
ADR-025에 따라 실행별 독립 PostgreSQL DB를 소유 단위로 사용한다. 기존 행 단위 정리·공유 테이블 전제는 DB 단위 소유권 검증과 명시적 정리 계약으로 대체한다. 성공 처리량은 DB 이력과 검증된 TPS이며 전체 HTTP RPS는 보조 지표다.

# ADR-023: APM 활성화 전환과 서버 실행 환경의 실험 검증 계약

## 상태
Accepted

## 컨텍스트
쿠폰 발급 API에서 직접 구현한 APM을 끈 상태와 켠 상태의 p95 지연시간 및 성공 처리량을 공정하게 비교하려면 두 모드 간 차이를 APM 계측 동작에 집중시켜야 한다(ADR-008·019). 잘못된 모드, JVM 시작 시점의 차이, 준비되지 않은 DB, 불일치한 컨테이너 자원이나 누락된 증거는 비교 결과를 무효화할 수 있다. ADR-022는 Makefile 및 스크립트 자동화를 확정했지만 APM 전환·서버 시작·준비 상태 검증은 아직 구체화하지 않았다. 또한 기존 ADR-019의 모드별 1회 Warm-up은 각 실행마다 서버를 시작하는 정책과 양립하기 어려워 사용자 승인하에 함께 개정한다.

## 결정
1. **APM 전환 — 환경 변수와 서버 재시작:** Spring Boot 설정 `apm.enabled: ${APM_ENABLED:true}`를 사용하되 성능 실험에서는 `APM_ENABLED=true|false`를 반드시 명시한다. 측정 중 런타임 토글은 제공하지 않는다. OFF에서는 APM 추적 `HandlerInterceptor`를 등록하지 않고 Monitor를 실행하지 않으며 Stack Trace 수집과 X-View 기록을 하지 않는다. ON에서는 같은 발급 Controller·Service 코드 위에 APM 계측 구성요소를 활성화한다. APM 조회 API는 OFF에서도 접근 가능하되 신규 추적 기록은 생성되지 않는다. 시작 시 조건부 Bean/설정을 사용하며 실제 비활성화·활성화는 실행 검증으로 확인한다.
2. **서버 환경 — 동일 이미지의 Docker Compose:** Spring Boot와 PostgreSQL을 Docker Compose로 실행한다. ON/OFF 모두 동일 Git 커밋에서 만든 **같은 애플리케이션 이미지 ID/digest**, Java 21 실행 환경, JVM 옵션(힙·GC 포함), CPU·메모리 제한, 커넥션 풀·DB 버전 및 설정을 사용한다. 모드 전환에 따라 애플리케이션 컨테이너를 재생성하되 PostgreSQL은 동일 설정과 영속 볼륨을 유지한다. 이미지 재빌드는 모드 전환 과정에서 수행하지 않는다. Locust는 기본 재현 범위에서 호스트의 독립 Python 프로세스(단일 프로세스)로 실행한다. 주요 리소스 설정과 도구 버전은 Manifest에 기록한다. 다른 호스트에서 절대 p95가 같아야 한다고 주장하지 않는다.
3. **APM 및 준비 상태 검증 — 조회 API + 발급 스모크 테스트:** 벤치마크 전용 프로파일에서만 `GET /internal/benchmark/status`를 제공하고 `ready`, `apmEnabled`, `databaseReady`, `applicationVersion`, `gitCommit` 등을 반환한다. DB 상태는 애플리케이션 관점의 연결 확인으로 판단하며 Compose healthcheck/`service_healthy`로 종속 서비스 준비를 보조한다. 공개 재현 환경에서는 컨테이너의 호스트 공개 포트를 `127.0.0.1`에 바인딩하고 벤치마크용 상태 API를 공개 배포 프로파일에서 비활성화한다. 상태 API의 출력과 **실제 독립 쿠폰 발급(HTTP 201)**을 교차 검증한다. ON에서는 해당 발급의 X-View 기록 생성, OFF에서는 기록 미생성을 확인한다. 스모크 테스트용 쿠폰·요청은 Warm-up·측정용 풀과 분리하고 성능 통계에 넣지 않는다. 실제 모드 확인에 실패하면 측정을 시작하지 않는다.
4. **매 실행 재시작 및 Warm-up — ADR-019 개정:** 사전 측정 OFF 3회·ON 3회와 정식 측정 OFF 3회·ON 3회 **모든 실행 단위**에서 동일 이미지로 애플리케이션을 새로 시작하고 상태/스모크 검증 후 **60초 Warm-up**, 이어 **60초 측정**을 수행한다. Warm-up과 측정은 서로 다른 신규 쿠폰 풀을 사용하며 Warm-up 요청·성능 수치는 사전 요청 수 산정 및 정식 중앙값 비교에 포함하지 않는다. 사전 측정에는 소진되지 않을 임시 풀을 제공하고 정식 측정에는 ADR-017~019의 산정량을 사용한다. **정식 실행 순서 OFF → ON → ON → OFF → OFF → ON**, 최대 100명·초당 10명 증가·0.1~0.3초 대기, 정상 발급 p95·성공 RPS, 중앙값과 15% 판정은 유지한다. 실행 실패 시 동일한 서버 재시작·검증·Warm-up 절차를 반복한다. DB 컨테이너 및 영속 볼륨은 서버 재시작 과정에서 삭제하지 않는다.
5. **환경 동등성 및 유효성 — 고정 설정 + Manifest + 자동 검증:** 측정 전에 Git 커밋·이미지 ID·APM 모드·JVM 옵션·DB 연결·준비 데이터·Locust 부하 설정을 검증한다. 측정 도중 쿠폰 소진, 예상치 못한 HTTP 오류, APM 모드 불일치/변경, 서버·DB 장애, Locust 실행 실패·부하 조건 이탈이 있으면 해당 실행을 `INVALID`로 기록한다. 종료 후 요청/성공·실패 집계, p95, RPS, Active Registry 정리, 원본 CSV·로그·Manifest 및 환경 변동을 확인·보존한다. 무효 실행을 삭제하거나 중앙값에 포함하지 않으며 원인과 재실행을 추적한다(ADR-019·022). PostgreSQL의 캐시·WAL·데이터 누적과 호스트의 CPU·디스크 자원 경쟁은 완전히 통제할 수 없으므로 실행별 변동성을 공개한다. 편차가 크게 나타나면 독립 DB 환경 또는 분리된 부하 생성 환경을 후속 보완책으로 검토하며, 검증 없이 동일 환경이라고 주장하지 않는다.

## 근거
- 서버 시작 시 환경 변수로 모드를 고정하고 OFF에서 계측 Interceptor·Monitor를 제거하면 런타임 전환의 경쟁 조건 없이 APM 자체의 관측 비용을 비교하기 용이하다.
- 동일 이미지·JDK·JVM 옵션과 명시적 컨테이너 자원 설정은 실험 모드와 무관한 애플리케이션 차이를 줄이며, Manifest는 실제 설정의 일치 여부를 추적할 수 있게 한다.
- 설정 확인만으로는 추적 기능이 실제로 작동하는지 알 수 없으므로 상태 API와 발급 스모크 테스트를 병행한다.
- 매 실행 동일한 시작·예열 절차를 적용하면 모드 전환 시에만 재시작하는 방식보다 JIT·커넥션 풀 등 초기 상태 편차를 줄일 수 있다. 다만 Warm-up이 완전한 JVM 또는 DB 상태의 동일성을 보장하지는 않는다.
- 자동 유효성 판정과 원본 보존은 오류 발생 시 정상 요청만 골라 성능 결과로 제시하는 것을 방지한다.

## Trade-off 및 보완 대안
- **런타임 ON/OFF 토글:** 서버 재시작과 초기 JVM 상태 차이를 피할 수 있으나 추적 중 전환과 Active Registry 정리, 접근 통제 및 동시성 정책이 추가로 필요해 이번에는 제외한다. 재시작의 약점은 모든 실행에 동일한 60초 Warm-up으로 보완한다.
- **ON/OFF 서버를 동시에 유지:** 재시작 비용을 줄이지만 호스트 자원 공유와 컨테이너 간 차이가 새 편향을 만들 수 있으므로 제외한다.
- **호스트 JVM + PostgreSQL Docker:** 컨테이너 자원 제한을 회피할 수 있지만 호스트 JDK·운영체제 설정의 재현 비용이 증가하므로 동일 이미지의 Compose 구성을 채택한다.
- **앱·DB·Locust를 독립 머신에서 실행:** 자원 경쟁을 줄일 수 있지만 네트워크와 머신 관리 변수를 추가한다. 현재는 단일 호스트의 재현성을 우선하며 필요 시 확장한다.
- **환경 변수만 확인하거나 상태 API만 확인:** 설정은 확인되지만 실제 APM 동작을 입증하기 어려우므로 별도 발급과 X-View 기록 확인을 결합한다.
- **모드 변경 시에만 재시작 / 모드별 Warm-up 1회:** 총 실행시간은 짧지만 사전·정식 실행별 JVM 상태가 달라져 비교 조건이 불균형해질 수 있으므로 각 실행마다 재시작·예열한다.
- **매 실행 독립 PostgreSQL 환경:** 누적 데이터·DB 내부 상태를 더 강하게 격리할 수 있지만 DB 초기 상태 준비, 캐시 예열 및 ADR-022 데이터 보존 절차가 추가된다. 기본안에서는 동일 DB 설정·볼륨 유지와 환경 기록을 택하고 변동성이 크면 독립 DB 재실험을 고려한다.

## 결과
- Spring Boot 및 PostgreSQL Compose 구성, 조건부 APM Bean 등록, 벤치마크 전용 상태 API, 발급 스모크 테스트, 실행별 컨테이너 재시작·Warm-up·환경 검증 자동화가 필요하다.
- **ADR-019 Warm-up 조건을 개정한다.** 기존 'OFF/ON 각 60초 1회' 대신 사전·정식 **각 실행마다 서버 재시작 후 60초 Warm-up**을 수행한다. 그 밖의 실행 순서, 부하 조건, 쿠폰 수량 계산, 통계 및 무효 판정은 유지한다.
- 실행별 준비·측정·증거 보존 절차는 `make test-overhead`와 역할별 스크립트로 자동화하며, `make clean-run RUN_ID=...`에 의한 명시적 데이터 정리 원칙을 유지한다.
- Docker가 호스트 성능 차이, PostgreSQL 내부 상태, Locust와 서버의 자원 경쟁을 제거하지는 못하므로 실험 한계를 보고서에 기록한다.
- 설계 채택은 기능 구현 및 테스트 통과를 의미하지 않는다. 구현과 10시간 타이머는 아직 시작하지 않았다.

## 기술면접·보고서 설명 근거
1. **왜 런타임 토글 대신 환경 변수인가?** 실행 중 모드 전환 경쟁 조건을 제거하고, OFF에는 추적 자체가 등록되지 않도록 하기 위해서다. 재시작 차이는 실행별 동일 Warm-up으로 통제한다.
2. **왜 동일 Docker 이미지인가?** JDK·라이브러리·애플리케이션 빌드가 성능 비교 변수로 섞이지 않게 하기 위해서다. 하드웨어 성능 동일성을 보장하지는 않는다.
3. **왜 상태 API 외에 발급 스모크 테스트도 하는가?** 설정값과 계측 기능의 실제 작동은 다른 문제이므로, ON의 X-View 기록 및 OFF의 미기록을 검증하기 위해서다.
4. **왜 매 실행 서버 재시작과 Warm-up인가?** JVM의 JIT·클래스 로딩·커넥션 풀 상태가 시작 후 요청량에 따라 바뀌므로 매 실험의 시작·예열 조건을 맞추기 위해서다. 완전한 상태 동일성을 주장하지 않는다.
5. **Docker만으로 동일 수치가 재현되는가?** 아니다. CPU·메모리·디스크·운영체제와 PostgreSQL 캐시 상태가 달라질 수 있으므로 환경과 변동성을 공개하고 결과 해석의 한계를 명시한다.

## 후속 결정 반영 (2026-11-08)
ADR-025에 따라 PostgreSQL 인스턴스는 공유하되 실행별 DB를 별도 생성하고 Spring Boot 재시작 시 JDBC URL의 데이터베이스 이름을 바꾼 뒤 실제 연결 DB를 검증한다.

# ADR-024: 문자열 사용자 ID, X-View 원본 보존 및 Slow 감지 보완

## 상태
Accepted

## 컨텍스트
구현 시작 전 설계 감사에서 숫자형 사용자 ID와 실행별 문자열 식별자의 불일치, APM X-View 조회 배열과 시각화용 메타데이터 JSON의 불일치, 100ms 주기 Monitor가 500ms 이상 실행 후 검사 사이에 종료되는 요청을 놓칠 수 있는 문제가 확인되었다. 구현이 아직 시작되지 않았으므로 사용자 ID는 기존 숫자형을 고수할 이유가 없으며 문자열로 통일한다.

## 결정
1. **사용자 ID를 문자열로 통일:** 쿠폰 발급 API의 `userId`, Service 인자, 발급 이력 엔티티의 `userId`, PostgreSQL `coupon_issues.user_id`, 테스트 데이터 및 Locust 입력을 모두 문자열로 통일한다. DB는 `VARCHAR(100) NOT NULL`, 공백 문자열 방지 CHECK, `UNIQUE(coupon_id, user_id)`를 사용한다. API는 null, 빈 문자열, 공백만 있는 값, 100자 초과를 HTTP 400으로 거부한다. 유효한 ID는 입력값 그대로 저장하고 비교하며 대소문자를 구분한다. `runId`는 실험 식별자로 별도 보존하되, 실행별 네임스페이스를 포함한 문자열 `userId`를 사용할 수 있다. ADR-002, ADR-003의 기존 숫자형 사용자 ID 및 양수 검증 계약은 본 결정으로 변경한다.
2. **X-View 원본과 변환본 모두 보존:** 기존 `GET /api/apm/xview`의 배열 응답을 유지한다. 수집 스크립트가 `xview-raw.json`에 원본을 보존하고 Manifest의 `experiment`, `apmEnabled`, `capturedAt`을 결합하여 `xview.json`을 생성한다. `transactionId`를 `id`로 매핑하고 `startedAt`, `elapsedMs`는 의미와 값을 보존한다. 건수·식별자·필드 값·중복 여부를 검증하고 실패 시 증거 생성 실패로 처리한다. `xview.png`는 변환본으로 생성한다. X-View의 최근 1,000건은 전체 부하 원본이 아니며 p95·성공 TPS는 Locust 상세 측정 원본으로 산출하고 TPS는 DB 발급 이력과 교차 검증한다. ADR-021의 API DTO와 시각화 JSON 일치 여부 미확정 항목은 이 변환 계약으로 해결한다.
3. **Slow 감지 보완:** 100ms Monitor 검사와 요청 완료 시 500ms 이상 여부 판정을 병행한다. Monitor가 실행 중인 요청의 Stack Trace를 먼저 캡처하는 것을 우선하고, 완료 시점까지 캡처되지 않은 Slow 요청은 해당 요청 처리 스레드의 완료 처리 과정에서 보완 캡처한다. 원자적 상태 전환으로 요청당 Stack Trace 수집 시도를 최대 한 번으로 제한하고 SlowTrace 중복 기록을 방지한다. 출처를 `MONITOR` 또는 `COMPLETION_FALLBACK`으로 기록한다. 보완 캡처는 실제 지연 지점의 스택을 보장하지 않으므로 병목 원인의 직접 증거로 과장하지 않는다. 완료된 요청은 Active Registry에서 제거하고 Thread 참조를 유지하지 않는다. 캡처 실패도 실패 상태와 사유를 기록하며 무한 재시도하지 않는다. 기존 500ms 임계값, 100ms 주기, 64프레임 상한은 유지한다.

## 근거
- 구현 전에는 문자열 식별자로 통일하는 편이 불필요한 숫자 ID 할당과 매핑을 제거하며 실행별 고유 사용자 ID를 표현하기 쉽다.
- X-View 원본과 변환본을 함께 공개하면 API 계약을 변경하지 않고 시각화 데이터의 출처와 변환 정확성을 검증할 수 있다.
- Monitor만으로는 경계 시점의 탐지 누락이 발생할 수 있으므로 완료 시 판정으로 보완하고, 원자적 제어와 수집 출처 표시로 중복과 해석 오류를 줄인다.

## 대안 및 Trade-off
- **숫자 ID + Manifest 매핑:** 기존 타입을 유지하지만 구현 전부터 불필요한 숫자 할당·충돌 검증이 필요하여 제외한다. **User 엔티티 추가:** 식별자 관리는 명확해지지만 현재 MVP 범위를 확대하므로 제외한다. 문자열 ID는 입력 길이와 공백 검증을 추가하는 비용을 감수한다.
- **API를 시각화 객체 형식으로 변경:** 변환이 사라지지만 기존 APM 조회 계약을 바꾼다. **변환본만 보존:** 파일은 적지만 변환 오류 검증이 어려우므로 원본도 함께 보존한다.
- **Monitor 주기를 10ms로 단축:** 누락 가능성은 줄지만 완전히 제거하지 못하고 오버헤드가 증가한다. **완료 시 판정만 사용:** 임계값 판정은 정확하지만 실제 대기 중 스택을 놓치므로 Monitor와 병행한다. 보완 캡처의 병목 증거력이 낮다는 한계는 출처 표시로 관리한다.

## 결과
- API 요청/응답, 엔티티, DB 컬럼, 검증 및 테스트 Fixture에서 `userId`는 문자열로 일관되게 사용한다. `runId`와 사용자 ID는 논리적으로 구별한다.
- 증거 경로에 `docs/evidence/lock-wait/xview-raw.json`이 추가된다. 원본-변환 건수·값 일치 검증을 자동화한다.
- SlowTrace에는 수집 출처와 캡처 실패 정보가 필요하며 Monitor와 완료 경로의 경쟁 테스트, 500~600ms 사이 완료 테스트, Thread 참조 정리 테스트를 추가한다.
- 실제 구현과 통합 테스트는 아직 수행되지 않았다.

## 기술면접·보고서 설명 근거
1. **왜 문자열 사용자 ID인가?** 구현 전 계약을 통일해 실행별 네임스페이스를 직접 표현하고 숫자 ID 매핑 비용을 제거하기 위해서다.
2. **문자열 사용자 ID의 위험은?** 공백·길이·대소문자 정책을 고정하고 DB CHECK·UNIQUE로 보호한다.
3. **왜 X-View 원본을 보존하는가?** 변환본의 건수와 필드 값이 실제 API 응답과 일치하는지 재검증하기 위해서다.
4. **왜 Monitor와 완료 판정을 함께 사용하는가?** 실행 중 병목 스택을 확보하면서 검사 간격 사이 종료된 느린 요청의 누락을 방지하기 위해서다.
5. **왜 캡처 출처를 구분하는가?** 완료 처리 스택을 실제 DB 대기 중 스택으로 잘못 해석하지 않기 위해서다.

# ADR-025: 요청별 성능 원본, 성공 TPS 및 실행별 독립 PostgreSQL 데이터베이스

## 상태
Accepted

## 컨텍스트
APM ON/OFF 성능 비교의 성공 처리량과 p95를 원본 요청에서 재계산하고, 실제 커밋된 쿠폰 발급과 대조해야 한다. 이전 실행의 발급 이력과 테이블 크기가 후속 실행에 섞이지 않도록 논리적 데이터 격리가 필요하다. 사전 측정 초기 쿠폰 수량, 경계 요청 처리, 부하 생성기 기록 오버헤드와 실행 간 변동성 판정도 명시해야 한다. 기존 ADR-019의 OFF/ON 각 3회, 60초, 15% 목표 및 ADR-022의 실행 증거 보존은 유지한다.

## 결정
1. **요청별 성능 원본:** Locust 단일 프로세스에서 요청 완료 이벤트를 크기가 제한된 메모리 큐에 전달하고 별도 CSV Writer가 `requests.csv`에 기록한다. `runId`, `phase`, `virtualUserIndex`, 문자열 `userId`, `couponId`, `startedAt`, `completedAt`, `httpStatus`, `responseTimeMs`, `success`, `error`를 보존한다. 큐 포화, 기록 오류, 누락, 종료 시 미배출 데이터는 실행을 `INVALID`로 처리한다. 기록 건수와 Locust 기본 통계의 요청 건수를 대조하고 클라이언트 CPU 등 부하 생성기 병목 가능성을 확인한다. 기본 Locust CSV는 교차 검증용이고 상세 원본이 성능 계산의 기준이다.
2. **정상 커밋 쿠폰 발급의 성공 TPS를 주 처리량 지표로 채택:** 정식 측정 60초 내에 완료된 HTTP 201 발급 응답 건수 `S`를 측정 원본으로 삼아 `성공 TPS = S / 60초`로 계산한다. 각 실행의 발급 대상 쿠폰과 PostgreSQL `coupon_issues`의 커밋된 이력을 요청별로 대조하여 성공 응답과 실제 발급이 일치하는지 검증한다. 요청별 DB 대조가 불가능하거나 불일치하면 `INVALID` 처리하고 원인을 보존한다. 측정 종료 시 진행 중이던 요청은 최대 15초 유예 동안 결과를 수집하되 정식 60초 TPS·p95 집계에는 포함하지 않고 별도 경계 요청으로 기록·DB 대조한다. 15초 내 미완료 요청은 `INVALID`이다. `전체 HTTP RPS = 정식 60초 내 완료된 전체 HTTP 요청 수 / 60초`는 보조 지표로 기록하며 상태 코드별 건수를 함께 남긴다. HTTP 201과 DB 커밋의 일치는 단순 건수뿐 아니라 쿠폰 ID·사용자 ID·발급 이력의 대응으로 검증한다. DB 커밋 시각과 HTTP 완료 시각이 다를 수 있으므로 DB 행의 시간 필드만으로 60초 경계를 판정하지 않는다.
3. **p95 및 비교 계산:** 정식 60초 내 완료된 HTTP 201 응답시간을 오름차순으로 정렬하고 `p95 = x[ceil(0.95 × N)]`(1부터 시작하는 Nearest-Rank)로 계산한다. N=0이면 `INVALID`이다. OFF/ON 각 3회 유효 실행의 p95 중앙값과 성공 TPS 중앙값을 각각 구한다. `p95 증가율 = (ON p95 중앙값 / OFF p95 중앙값 - 1) × 100`, `성공 TPS 감소율 = (1 - ON TPS 중앙값 / OFF TPS 중앙값) × 100`으로 계산하며 각각 15% 이하가 AC07 목표다. 정상 요청만 선별해 예기치 않은 오류를 은폐하지 않도록 기존 INVALID 규칙을 적용한다. 전체 HTTP RPS는 보조 통계로만 제시한다.
4. **실행별 독립 PostgreSQL 데이터베이스:** 동일 PostgreSQL 인스턴스·버전·설정·영속 볼륨을 유지하되 사전 측정, Warm-up, 정식 측정에 속하는 각 실행에 고유한 독립 데이터베이스를 생성한다. 각 DB는 버전 관리되는 동일 DDL·인덱스·제약조건을 적용하고 동일한 기준의 초기 쿠폰 수량과 재고(발급 대상 쿠폰 `total_stock=1`, `issued_count=0`, 발급 이력 0)를 검증한다. Spring Boot를 실행마다 재시작할 때 JDBC URL의 데이터베이스 이름을 변경하고 실제 연결 DB를 확인한다. Warm-up과 정식 측정의 쿠폰 풀은 서로 구분한다. DB 이름, 소유 `runId`, 초기 데이터·발급 이력, DDL 버전, PostgreSQL 버전, 환경·용량을 Manifest에 기록한다. 완료 후 자동 DB 삭제는 금지하며 명시적 `make clean-run RUN_ID=...`에서 소유권·대상 DB를 검증한 뒤 해당 실행 DB만 정리한다. 데이터베이스 단위의 삭제는 파괴적이므로 별도 명시적 확인을 요구한다. 기존 ADR-022의 행 단위 정리 방식은 본 결정의 실행별 DB 소유 범위 정책으로 개정한다.
5. **초기 쿠폰 수량:** Locust 사용자별 순차 발급과 최소 요청 대기 0.1초, 60초 측정 조건에서 사전 측정 및 Warm-up에 사용자당 **601개**의 쿠폰을 기본 준비한다. 이는 첫 요청·경계 여유를 고려한 보수적 상한이며 실제 처리량 예측값이 아니다. 내부 재시도나 추가 발급 요청을 허용하지 않는다. 정식 측정은 기존 ADR-019에 따라 유효한 사전 OFF/ON 6회에서 관측한 사용자별 성공 발급 수의 전역 최댓값 `M`에 대해 사용자당 `ceil(2 × M)`개를 준비한다. 풀 소진이나 할당 오류는 `INVALID`이다.
6. **실험 변동성 및 산출물:** 같은 모드의 유효한 정식 3회에서 p95 또는 성공 TPS의 `최댓값 / 최솟값 > 1.15`이면 `REVIEW_REQUIRED`로 표시한다. 이는 통계적 유의성 검정이나 자동 제외 조건이 아니라 추가 검토 신호다. `VALID/INVALID`와 성능 목표 `PASS/FAIL`은 분리한다. 실행별 `manifest.json`, `requests.csv`, `locust_stats.csv`, `validation.json`, 경계 요청 및 DB 교차 검증 기록을 보존하고, `comparison.csv`를 상세 원본에서 재생성 가능하게 한다. Warm-up 기록은 별도 저장하고 정식 통계에 포함하지 않는다.

## 근거
- 상세 요청 원본과 DB 커밋 이력을 함께 검증하면 단순 HTTP 성공 응답만을 실제 발급 성공으로 오인할 위험을 줄일 수 있다. 발급 성공 TPS는 이 프로젝트의 핵심 비즈니스 트랜잭션 처리량을 직접 표현한다.
- 별도 Writer는 파일 I/O를 Locust 요청 완료 경로에서 분리하며, 제한된 큐·건수 검증·오류 시 INVALID 정책으로 기록 손실을 드러낸다.
- 실행별 독립 DB는 스키마 분리보다 JDBC 연결 대상과 데이터 소유 범위가 명확하며, 동일 DDL과 초기 상태를 사용했다는 사실을 포트폴리오에서 설명하기 쉽다.
- 601개는 60초/0.1초의 보수적 상한에 경계 여유를 둔 값이고, 정식 실험은 사전 관측 최대치의 2배라는 기존 계약을 유지한다.
- 동일 모드의 변동성 검토는 중앙값이 가릴 수 있는 실행별 불안정성을 별도로 보여준다.

## 대안 및 Trade-off
- **기본 Locust 집계 CSV만 사용:** 기록 비용은 작지만 HTTP 201 요청별 p95와 DB 이력 대응을 독립적으로 검산하기 어렵다. **요청마다 동기 CSV 쓰기:** 단순하지만 클라이언트 I/O가 부하를 제한할 수 있다. **종료 시 일괄 메모리 저장:** 런타임 I/O는 적지만 비정상 종료 시 원본 손실이 크다. 제한 큐와 별도 Writer를 채택하되 부하 생성기 오버헤드와 큐 포화를 검증한다.
- **전체 HTTP RPS를 주 지표로 사용:** API 서버 전체 응답량은 표현하지만 오류 응답도 포함해 성공 발급 트랜잭션의 처리량을 흐릴 수 있다. 성공 TPS를 주 지표로 하고 전체 RPS를 보조로 남긴다. **DB 발급 건수만으로 TPS 산출:** 실제 커밋 확인에는 강하지만 HTTP 측정 경계·응답시간과 직접 연결하기 어려워 요청별 HTTP 원본과 DB 이력을 교차 검증한다.
- **동일 테이블에서 실행별 행 분리:** 구현은 단순하지만 테이블이 누적된다. **실행별 독립 스키마:** 테이블 격리는 가능하지만 연결 대상과 소유권 설명이 상대적으로 간접적이다. **실행별 독립 PostgreSQL 컨테이너·볼륨:** 프로세스 자원까지 더 분리하지만 시작·예열·스토리지 관리 비용이 크다. 동일 인스턴스+독립 DB를 선택한다. 단 PostgreSQL 공유 버퍼, WAL, 디스크 I/O, CPU·메모리 등 물리적 자원은 여전히 공유하며, 논리적 격리를 물리적 격리로 주장하지 않는다.
- **사전 수량 256개부터 증설:** 초기 시딩량은 적지만 소진 시 재측정이 필요하다. **추가 예비 측정:** 수량을 줄일 수 있으나 단계가 늘어난다. **측정 중 쿠폰 추가:** 시딩 부하가 측정에 개입한다. 601개 선준비를 선택한다.
- **동일 모드 편차가 큰 실행을 자동 제외:** 결과 선택 편향이 생길 수 있으므로 제외하지 않고 REVIEW_REQUIRED로 표시한다. 3회 반복만으로 통계적 유의성을 주장하지 않는다.

## 결과
- AC07 주 처리량 명칭을 성공 RPS에서 **정상 커밋된 쿠폰 발급의 성공 TPS**로 개정한다. HTTP 201 상세 원본으로 계산하고 DB 발급 이력과 요청별로 검증하며 전체 HTTP RPS는 보조로 남긴다.
- 실행마다 독립 PostgreSQL 데이터베이스와 JDBC URL 변경·연결 검증이 필요하다. 실행별 DB의 보존과 명시적 정리 정책을 적용한다.
- 요청별 CSV Writer, 경계 요청 처리, 검증 보고서, 변동성 경고와 DB 대조 자동화가 구현 범위에 추가된다.
- 60초, 100 users, 초당 10 users 증가, 요청 간 0.1~0.3초 대기, 사전·정식 각 OFF/ON 3회, 실행별 60초 Warm-up, 15% 성능 목표는 유지한다.
- 아직 구현이나 실제 성능 측정은 수행되지 않았다.

## 기술면접·보고서 설명 근거
1. **왜 TPS인가?** 이 프로젝트의 핵심 비즈니스 작업은 정상 커밋된 쿠폰 발급이다. HTTP 201을 측정 원본으로 삼고 DB 발급 이력과 요청별 대조하여 성공 TPS로 보고한다. 전체 HTTP RPS는 오류를 포함하는 보조 지표다.
2. **왜 독립 데이터베이스인가?** 실행마다 별도 DB를 만들고 JDBC URL의 DB 이름으로 연결 대상을 명확히 통제하며, 동일한 DDL과 초기 데이터로 실험을 준비했음을 설명하기 쉽다.
3. **독립 DB가 완전 격리인가?** 아니다. 동일 PostgreSQL 인스턴스의 공유 버퍼·WAL·디스크·CPU를 공유하므로 물리적 자원 간섭 가능성은 남는다.
4. **왜 상세 CSV를 비동기로 저장하는가?** p95·TPS를 재계산할 원본을 확보하면서 파일 I/O를 요청 처리 경로에서 분리하기 위해서다. 큐 포화와 기록 누락은 INVALID로 판정한다.
5. **왜 601개인가?** 최소 대기 0.1초와 60초의 순차 요청 상한에 경계 여유를 둔 수량이며, 정식 수량은 사전 관측 최댓값의 2배로 산정한다.
6. **왜 REVIEW_REQUIRED인가?** 같은 모드의 실행별 편차를 드러내기 위한 검토 표시이며 유효한 결과를 임의로 제외하거나 통계적 유의성을 주장하지 않는다.

# ADR-026: AC01~AC11 테스트 상세설계 및 검증 증거 계약

## 상태
Accepted

## 컨텍스트
ADR-008의 11개 인수 조건을 구현·재현할 테스트 계층, Fixture, 실행 절차, Assertion 및 증거를 명확히 해야 한다. ADR-020의 PostgreSQL 행 잠금 대기 3초 제한, ADR-024의 Monitor 및 완료 시 보완 판정, ADR-025의 정상 커밋 쿠폰 발급 성공 TPS와 실행별 독립 PostgreSQL 데이터베이스 계약을 준수해야 한다. 테스트 편의를 위한 비즈니스 우회 API나 임의의 측정 결과를 만들지 않는다.

## 결정
1. **테스트 계층:** APM 정책과 Buffer는 Unit Test, 동시 발급·중복 발급·재고 제약은 실제 PostgreSQL Integration Test, 실제 잠금 대기·시간 초과·APM 정리·ON/OFF 정합성은 HTTP Integration Test, 오버헤드는 Locust E2E에서 검증한다. 공통 Fixture 및 Assertion을 재사용하되 계층별 검증 책임을 구분한다.
2. **재고 30개에 서로 다른 사용자 100명이 동시 발급하는 정합성 검증 (AC01):** 커밋된 재고 30 쿠폰과 서로 다른 문자열 `userId` 100개를 준비하고 `ExecutorService`·`CountDownLatch`로 동시 시작시킨다. **성공 30건, 최종 `issued_count=30`, 발급 이력 30건, 잔여 재고 0 및 초과 발급 없음**을 필수로 확인한다. 나머지 70건은 정의된 실패 응답만 허용하며 재고 소진 409 외 PostgreSQL 잠금 대기 제한에 따른 503은 별도 집계·진단한다. 503 때문에 성공이 30건에 미달하면 통과 처리하지 않는다. 실패 요청을 성공 수에 맞추기 위한 자동 재시도는 금지한다. 시작 신호는 DB 트랜잭션이 동시에 잠금을 획득한다는 보장을 뜻하지 않는다.
3. **동일 사용자 20건 동시 발급 방지 (AC02):** 재고 30 쿠폰과 동일 문자열 사용자 1명을 준비한다. 발급 성공 1건, 중복 발급 오류 19건, 이력 1건, `issued_count=1`, 잔여 재고 29를 엄격히 검증한다. `UNIQUE(coupon_id,user_id)`가 적용되었는지도 확인한다. 예상치 않은 503은 성공·중복 응답 계약을 충족하지 못한 것으로 기록한다.
4. **재고 0 쿠폰 발급 거부 (AC03):** 미발급 사용자에게 HTTP 409 `COUPON_SOLD_OUT`, 발급 이력 0건 및 `issued_count=0`을 확인한다. 이미 발급한 동일 사용자와 재고 소진이 겹치면 `COUPON_ALREADY_ISSUED`가 우선하는 기존 오류 우선순위도 추가 검증한다.
5. **500ms SlowTrace 기준과 검사 간격 누락 보완 (AC04):** Fake Clock 또는 제어 가능한 시간을 사용해 499ms 미만은 미기록, 500ms 이상은 기록함을 검증한다. Monitor가 490ms에 마지막 검사하고 요청이 550ms에 종료되는 경우 `COMPLETION_FALLBACK`이 SlowTrace를 1회 기록해야 한다. Monitor에서 이미 기록한 요청은 완료 시 중복 기록하지 않는다.
6. **Stack Trace 수집 최대 1회·1~64프레임 (AC05):** Monitor/완료 경로의 동시 캡처 경쟁을 재현해 원자적 권한 획득과 요청별 최대 한 번의 수집 시도를 검증한다. 정상 캡처 프레임은 1~64개, 캡처 출처는 `MONITOR` 또는 `COMPLETION_FALLBACK`으로 기록한다. 캡처 실패는 실패 사실·사유를 남기되 무제한 재시도를 하지 않는다. 완료 시점 캡처는 실제 대기 중 병목 스택이라는 증거로 사용하지 않는다.
7. **X-View 최근 완료 요청 1,000개 보관 (AC06):** 서로 다른 완료 요청 1,200개를 순서대로 추가하면 201~1200번만 오래된 순서로 남고 1~200번은 제거되어야 한다. 동시 삽입·조회, 조회 중 내부 상태 불변, SlowTrace 최근 100건 제한도 보조 테스트로 확인한다.
8. **APM ON/OFF p95와 성공 TPS 오버헤드 15% 이하 (AC07):** `make test-overhead`로 Locust 최대 100명·초당 10명 증가·요청 간 0.1~0.3초·매 실행 60초 Warm-up/60초 정식 측정, 사전 OFF/ON 각 3회 및 정식 `OFF,ON,ON,OFF,OFF,ON` 순서로 실행한다. 사용자별 독립 쿠폰 풀, 사전·Warm-up 601개/사용자, 정식 `ceil(2M)`개/사용자, 실행별 독립 PostgreSQL DB와 모드별 서버 재시작·검증을 적용한다. 정식 60초 내 완료된 HTTP 201 중 DB 커밋과 대응하는 건수로 성공 TPS를 계산하고 HTTP 201 응답시간 Nearest-Rank p95를 계산한다. OFF/ON 각 3회 중앙값 비교에서 p95 증가율과 TPS 감소율 각각 15% 이하를 목표로 한다. 전체 HTTP RPS는 보조 지표다. 유효성(`VALID/INVALID`), 목표(`PASS/FAIL`), 동일 모드 편차 진단(`REVIEW_REQUIRED`)을 구분한다. 요청별 CSV, Locust 원본, Manifest, DB 대조 및 비교표를 보존한다. 측정 종료 후 최대 15초의 진행 중 요청 유예와 경계 요청 별도 기록은 ADR-025를 따른다.
9. **실제 PostgreSQL 행 잠금 대기에서 SlowTrace 수집 (AC08):** 커밋한 쿠폰 Fixture에 별도 JDBC 연결·트랜잭션으로 `SELECT ... FOR UPDATE`를 실행해 잠금을 확보하고, 실제 HTTP 발급 요청을 보낸다. `pg_stat_activity`의 잠금 대기와 `pg_blocking_pids()` 등으로 실제 차단 관계를 확인한 후 약 1초(3초 미만)에 잠금을 해제한다. HTTP 201, DB 발급 이력, SlowTrace, X-View와 PostgreSQL 관측 시각·로그를 검증·보존한다. 실제 대기 중 스택 확보의 증거는 `MONITOR` 출처의 캡처로 한정하며 완료 경로의 캡처만으로 AC08을 입증했다고 주장하지 않는다.
10. **PostgreSQL 행 잠금 3초 대기 제한 및 503 오류 (AC09):** 별도 트랜잭션으로 잠금을 3초보다 오래 유지해 동일 발급 트랜잭션의 `SET LOCAL lock_timeout='3s'` 경로를 실행한다. PostgreSQL SQLSTATE `55P03`의 잠금 문맥을 확인하고 HTTP 503 `COUPON_LOCK_TIMEOUT`, 발급 이력 증가 없음, 재고 변경 없음, 트랜잭션 롤백, 자동 재시도 없음, APM 기록·Active Registry 정리를 검증한다. HTTP 전체 시간 3초 정확히 일치는 요구하지 않는다.
11. **요청 종료 후 Active Registry의 Thread 참조 제거 (AC10):** HTTP 201/409/503 경로를 통과한 요청의 거래 식별자가 Active Registry에서 제거되는지 확인하고 완료 기록·API 응답 DTO에 `Thread` 객체가 남거나 노출되지 않는지 검증한다.
12. **APM OFF/ON에서 동일한 쿠폰 발급 정합성 (AC11):** APM 비활성·활성의 독립 Spring Boot 컨텍스트 또는 서버 시작 구성에서 실제 HTTP로 동시 발급, 동일 사용자 중복 발급, 품절을 재검증한다. 공유 Fixture/Assertion을 재사용하며 성능 수치의 동일성을 요구하지 않고 비즈니스 정합성 및 오류 계약의 일치를 확인한다.
13. **공통 데이터·실행·증거:** 모든 Fixture는 병렬 요청 시작 전 커밋하며 테스트별 고유 쿠폰·문자열 사용자를 사용하고 실행 소유 데이터만 정리한다. 완료되지 않은 비동기 작업이나 잠금 보유 트랜잭션을 남긴 채 DB를 검증·정리하지 않는다. `make test-unit`(AC04~06), `make test-integration`(AC01~03과 HTTP 정합성), `make test-lock-wait`(AC08~10), `make test-overhead`(AC07), `make evidence`(결과 검증·집계·시각화)를 공개 진입점으로 사용하며 AC11은 공통 HTTP 정합성 경로에 포함한다. `docs/evidence/ac-results.md`, `test-results.txt`, `lock-wait/{pg-wait.txt,slow-traces.json,xview-raw.json,xview.json,xview.png}`, `overhead/`의 원본·Manifest·DB 교차검증·비교 결과에 AC별 증거를 연결한다. 구현·테스트를 실행하기 전 PASS 또는 성능 수치를 기록하지 않는다.

## 근거
- 실제 PostgreSQL에서 발급 정합성을 확인하면서 APM 내부 정책은 제어 가능한 단위 테스트로 검증하면 실패 원인을 분리할 수 있다. 핵심 경로는 HTTP 통합 테스트로 다시 검증한다.
- 실제 잠금 대기 입증은 느린 HTTP 응답 하나로 충분하지 않다. PostgreSQL 차단 관계, APM SlowTrace, HTTP 결과를 같은 실행에서 확인해야 한다.
- 3초 DB 잠금 제한과 동시 발급 정합성은 구별한다. AC01은 성공 30건과 재고 정합성이 필수이며 503은 별도 분석한다. AC02는 이미 합의된 1성공·19중복 오류를 엄격히 확인한다.
- AC07은 원본 요청/커밋 대조, 실험 유효성, 성능 목표를 분리해 실패한 성능 결과를 선택적으로 제거하지 않는다.

## 대안 및 Trade-off
- **모든 동시성 테스트를 HTTP E2E로 수행:** 전체 경로를 검증하지만 네트워크·서버·커넥션 풀 요인으로 DB 정합성 실패 원인을 분리하기 어렵다. **서비스+PostgreSQL 통합 테스트 기본, AC11에서 실제 HTTP 재검증**으로 두 목표를 보완한다.
- **HTTP 응답 지연만으로 AC08 입증:** 쉬우나 DB 잠금 원인을 알 수 없다. **Stack Trace만 확인:** DB 내부 차단 상태의 직접 증거가 부족하다. **PostgreSQL 대기·SlowTrace·HTTP 결과 결합**을 선택한다. 증거 수집 복잡도는 실제 병목 입증을 위해 감수한다.
- **데모용 잠금 API 및 Thread 디버그 API 추가:** 테스트 편의성은 높지만 프로덕션 대상 코드에 우회 경로를 도입한다. 별도 JDBC 연결과 테스트 코드 내부 확인을 사용하고, ADR-023에서 승인된 접근 제한형 벤치마크 상태 조회 API만 예외로 유지한다.
- **동시성 테스트의 일시 실패를 자동 재시도로 보정:** 통과율을 높이는 듯 보이나 원래의 동시 요청 조건을 바꾸고 실패를 숨긴다. 자동 보정 없이 실제 결과·최종 DB 상태·오류 종류를 기록한다.

## 결과
- 11개 인수 조건별 테스트 계층, 클래스 후보(`CouponIssueConcurrencyIT`, `CouponIssueServiceIT`, `SlowTransactionMonitorTest`, `SlowTraceCaptureTest`, `XViewBufferTest`, `PostgresLockWaitHttpIT`, `PostgresLockTimeoutHttpIT`, `ApmLifecycleHttpIT`, `ApmEnabledCouponHttpIT`, `ApmDisabledCouponHttpIT`)와 Fixture/Assertion/증거 계약이 확정된다. 클래스명은 구현 명세상의 후보로, 테스트 경계와 검증 책임이 우선이다.
- PostgreSQL 잠금 대기를 관찰하지 못했거나 `MONITOR` 출처 캡처를 얻지 못한 AC08은 실행 중 병목 스택 확보까지 PASS로 주장하지 않는다.
- AC01의 503은 정합성 오류와 구별하여 기록하지만, 성공 30건 미달을 허용하는 예외로 사용하지 않는다. AC02의 19건 중복 응답 조건은 유지한다.
- 구현 및 실제 테스트 통과 여부는 아직 검증하지 않았다. 구현 10시간 타이머는 문서·WBS 동결 후 시작한다.

## 기술면접·보고서 설명 근거
1. **왜 계층을 분리했나?** DB 정합성·APM 내부 정책·실제 HTTP 계측·성능 비교는 검증 대상이 달라 각각 적합한 계층에서 확인하고 핵심 통합 경로를 HTTP로 교차검증하기 위해서다.
2. **왜 PostgreSQL 대기 상태를 직접 수집했나?** 느린 응답이나 Java 스택만으로 잠금 원인을 단정할 수 없으므로 DB의 실제 차단 관계와 APM 기록을 연결하기 위해서다.
3. **왜 503을 AC01에서 따로 기록하나?** 3초 잠금 대기 제한에 따른 처리 거부와 재고 초과 발급이라는 정합성 문제를 구별하기 위해서다. 단 정확히 30건 성공해야 한다는 통과 조건은 유지한다.
4. **왜 VALID와 PASS를 분리하나?** 실험이 유효했어도 15% 목표에 실패할 수 있으며, 그 결과를 임의로 제외하면 선택 편향이 생기기 때문이다.

# ADR-027: Warm-up과 정식 측정의 Locust 세션 경계

## 상태
Accepted

## 컨텍스트
ADR-019, ADR-023, ADR-025, ADR-026은 실행별 독립 PostgreSQL 데이터베이스, 실행마다 Spring Boot 재시작, Warm-up 60초 및 정식 측정 60초, Locust 최대 100명·초당 10명 증가를 확정했다. 여기서 **실행별 독립 DB는 서로 다른 실험 실행 간 격리**를 뜻하며, 동일 실행의 Warm-up과 정식 측정은 원래부터 **동일한 Spring Boot 프로세스 및 PostgreSQL 데이터베이스**를 사용한다. 두 구간의 쿠폰 풀만 구분한다. 기존 결정은 변경하지 않는다.

다만 Warm-up에서 생성된 가상 사용자 100명이 정식 측정에 그대로 남으면 정식 측정에서 0명부터 초당 10명씩 증가시키는 부하 조건을 재현하지 못한다. 따라서 Locust 클라이언트 세션의 경계를 명시할 필요가 있다.

## 결정
1. 실험 실행 1회마다 독립 PostgreSQL 데이터베이스를 생성하고 Spring Boot를 한 번 시작한다. APM 상태와 DB 연결 대상을 확인한다.
2. **Warm-up과 정식 측정은 별도 Locust 세션**으로 실행한다. 각 세션은 가상 사용자 0명에서 시작해 최대 100명까지 초당 10명씩 증가시키고, 각 60초 동안 실행한다.
3. Warm-up 세션의 종료와 진행 중 요청 정리를 확인한 다음 정식 측정 세션을 시작한다. 두 세션 사이에 **Spring Boot 프로세스 또는 PostgreSQL 데이터베이스를 재시작하거나 변경하지 않는다.** Warm-up과 정식 측정은 같은 DB 내의 서로 다른 쿠폰 풀을 사용한다.
4. Warm-up 요청은 정식 측정 통계에서 제외한다. 정식 측정은 해당 세션의 시작·종료 경계를 기록하고, 60초 내 완료된 요청만 주 지표에 포함한다. 진행 중 요청에 대한 최대 15초 종료 유예 및 경계 요청 별도 보존·DB 대조는 ADR-025를 따른다.
5. 세션별 원본과 실행별 Manifest에 세션 구분, 시작·종료 시각, 가상 사용자 증가 설정, 대상 DB 식별자 및 Spring Boot 프로세스 동일성 검증 결과를 남긴다.

## 근거
- 정식 측정에서도 사용자 0명에서 시작하는 초당 10명 증가 조건을 명확하게 재현한다.
- 부하 생성기인 Locust 세션만 분리하므로 애플리케이션 JVM Warm-up 효과와 DB 연결 환경은 유지된다.
- Warm-up과 정식 측정의 쿠폰 풀·측정 원본을 분리해 집계 오염을 방지한다.

## 대안 및 Trade-off
- **추천안 — 별도 Locust 세션:** 부하 시작 조건과 통계 경계가 명확하다. 단점은 세션 전환 자동화와 종료 확인이 필요하다는 점이며, Makefile/실험 오케스트레이션에서 종료 확인·시작 기록을 자동화해 보완한다.
- **동일 Locust 세션에서 통계만 초기화:** 클라이언트 세션 연속성은 유지하지만 이미 생성된 가상 사용자가 남아 정식 측정의 0명 시작·초당 10명 증가 조건을 만족하지 않는다.
- **동일 Locust 프로세스에서 사용자 수를 0으로 내렸다가 다시 증가:** 프로세스 재시작은 줄이지만 모든 사용자 종료·재생성과 통계 경계가 정확히 분리되었는지 추가 검증해야 한다.

## 이전 ADR과의 관계 및 변경 사유
- **ADR-019, ADR-023, ADR-025, ADR-026을 대체하지 않는다.** 해당 ADR의 실행별 DB 격리, 서버 재시작, Warm-up, 쿠폰 풀, 성능 지표와 종료 유예 결정을 그대로 유지한다.
- 본 ADR은 기존 문서에 명시되지 않았던 **Locust 세션 경계**만 구체화한 후속 결정이다. 기존 ADR의 본문·상태를 소급 수정하지 않는다.
- 향후 이전 결정을 실제로 변경해야 한다면 과거 ADR의 결정 본문은 보존하고, 새 ADR에 이전 결정·변경 이유·대안·대체 관계를 명시한다.

## 결과
- 정식 측정의 사용자 증가 조건과 집계 경계가 재현 가능해진다.
- 한 실험 실행의 Warm-up과 정식 측정은 동일 Spring Boot 프로세스·동일 PostgreSQL DB를 유지한다.
- 구현 및 실험 실행은 아직 시작하지 않았으며 실제 재현 여부는 검증 전이다.

## 기술면접·보고서 설명 근거
**왜 Locust 세션만 분리하는가?** Warm-up 효과는 서버에 유지하면서 정식 측정의 부하 생성 조건을 0명부터 동일하게 재현하기 위해서다. 세션 전환 시 서버나 DB를 바꾸지 않으므로 실험 실행 간 격리 원칙과도 충돌하지 않는다.

# ADR-028: APM 요청 생명주기와 Stack Trace 수집 동기화

## 상태
Accepted

## 컨텍스트
ADR-005는 `ConcurrentHashMap<UUID, ActiveTransaction>`에 실행 중 요청과 Thread 참조를 보관하고 `HandlerInterceptor.afterCompletion()`에서 정리하도록 결정했다. ADR-006은 100ms Monitor, 500ms Slow 기준과 최대 64개 Stack Frame을, ADR-024는 Monitor 캡처와 완료 시 보완 캡처 및 요청당 원자적 단일 캡처를, ADR-026은 이에 대한 테스트를 결정했다.

그러나 단순한 `AtomicBoolean` 기반 중복 방지만으로는 Monitor가 캡처를 시작하는 순간 HTTP 요청의 종료 처리가 시작되는 경쟁 상태를 해결할 수 없다. 중복 캡처 방지뿐 아니라 종료 중 신규 캡처 차단, 이미 진행 중인 캡처의 완료 확인, Thread 참조 정리 순서를 명확히 해야 한다.

## 결정
1. `ActiveTransaction`별로 요청 생명주기 `ACTIVE → COMPLETING → CLOSED`와 캡처 상태 `NOT_CAPTURED → CAPTURING → CAPTURED/FAILED`를 별도로 관리한다. 상태 변경은 `ActiveTransaction` 내부 메서드로 캡슐화한다.
2. Monitor는 요청이 `ACTIVE`이고 500ms 이상 경과한 경우에만 캡처 권한을 시도한다. **`ACTIVE` 검사와 `NOT_CAPTURED → CAPTURING` 전이는 요청별로 원자적으로 처리**한다. `COMPLETING` 이후 Monitor는 신규 캡처를 시작할 수 없다.
3. `afterCompletion()`은 먼저 `COMPLETING`으로 전환한다. 500ms 이상이며 캡처 상태가 `NOT_CAPTURED`라면 완료 경로에서 단 한 번 보완 캡처를 수행하고 출처를 `COMPLETION_FALLBACK`으로 기록한다. Monitor가 이미 캡처를 시작했다면 중복 캡처하지 않고 기존 캡처의 완료 결과를 확인한다.
4. 실제 `Thread.getStackTrace()` 호출은 상태 전이용 동기화 구간 **밖**에서 실행한다. 진행 중 캡처의 완료·실패는 요청별 완료 신호로 알리며, 캡처 수행자는 `try/finally`에서 신호를 반드시 완료한다. 예외 발생 시 `FAILED`로 확정하고 실패 사유를 기록한다. 완료 경로는 해당 신호를 동기화 구간 밖에서 확인한다.
5. 캡처 결과 확정 또는 실패 확인 후 완료 기록(`TransactionSample`)을 생성하고 Active Registry에서 해당 요청을 제거하며 Thread 참조를 해제한 뒤 `CLOSED`로 전환한다. 완료된 요청의 Thread 객체는 X-View 또는 SlowTrace 보관 기록에도 직접 포함하지 않는다.
6. 캡처 출처가 `MONITOR`라는 사실만으로 실제 PostgreSQL 대기 중인 Stack Frame을 확보했다고 단정하지 않는다. AC08은 PostgreSQL의 실제 차단·대기 상태와 캡처된 프레임을 함께 확인한다.

## 근거
- 요청 생명주기와 캡처 진행 상태를 분리해 종료와 수집의 경쟁을 명시적으로 제어한다.
- 요청별 짧은 동기화로 서로 다른 요청 사이의 전역 잠금 경합을 피한다.
- 캡처 실패 시에도 완료 신호와 정리 절차를 보장해 Thread 참조 누수를 방지한다.
- 완료 시 보완 캡처와 요청당 최대 한 번의 캡처 정책을 동시에 유지한다.

## 대안 및 Trade-off
- **추천안 — 상태 전이 + 요청별 짧은 동기화:** 종료 순서, 단일 캡처 및 참조 정리를 명확히 제어한다. 단점은 상태·완료 신호 관리가 복잡해진다는 점이다. 이를 `ActiveTransaction` 내부 상태 전이 메서드와 `try/finally` 완료 신호로 보완한다. 이미 시작된 캡처의 결과를 기다리는 비용은 발생할 수 있으나, 대기는 상태 잠금 밖에서 수행한다.
- **`AtomicBoolean` 하나로 캡처 권한 관리:** 구현과 비용이 단순하지만 종료 중 신규 캡처 차단 및 진행 중 캡처의 종료 순서를 함께 표현하기 어렵다.
- **Stack Trace 수집 전체를 `synchronized`로 보호:** 구현이 직관적이지만 스택 조회 동안 요청 종료 처리가 지연된다.
- **전역 단일 이벤트 처리 스레드로 직렬화:** 경쟁 상태가 감소하지만 한 요청의 캡처 지연이 다른 요청에 전파될 수 있다.

## 테스트 검증 계약
- T1: Monitor 선캡처 완료 → `MONITOR` SlowTrace 정확히 1건.
- T2: 완료 처리 선진입 → Monitor의 신규 캡처 차단.
- T3: Monitor 캡처 진행 중 요청 종료 → 기존 캡처 결과 확인 후 안전하게 Registry·Thread 정리.
- T4: Monitor와 완료 경로 동시 시도 → Stack Trace 캡처 시도 최대 1회.
- T5: Stack Trace 조회 예외 → `FAILED` 기록, 완료 신호 전달 및 정리.
- T6: 550ms 요청이 Monitor 다음 검사 전에 종료 → `COMPLETION_FALLBACK` 기록.
- T7: HTTP 201·409·503 종료 → Active Registry에 해당 Thread 참조 없음.
- T3·T4는 `CountDownLatch` 등으로 경쟁 순서를 제어해 재현한다. 단순 동시 실행만으로 경쟁 상태가 발생했다고 가정하지 않는다.

## 이전 ADR과의 관계 및 변경 사유
- **ADR-005, ADR-006, ADR-007, ADR-024, ADR-026을 대체하지 않는다.** Active Registry, Slow 기준, Monitor 주기, X-View, 완료 시 보완 캡처, 테스트 조건을 유지한다.
- ADR-024의 원자적 중복 캡처 정책에 **요청 종료와 캡처 완료 사이의 동기화 계약**을 추가한다. 이는 기존 결정의 번복이 아닌, 미정의된 경쟁 상태의 구현 계약을 구체화한 것이다.
- 이전 ADR의 원문·상태는 수정하지 않는다. 이후 기존 결정을 변경할 경우 새 ADR에서 변경 이유와 대체 관계를 기록한다.

## 결과
- 요청당 Stack Trace 캡처 시도 최대 1회, 완료 처리 이후 신규 Monitor 캡처 차단, 캡처 실패 시에도 요청 정리라는 검증 가능한 계약이 생긴다.
- 요청별 상태 관리와 완료 신호에 따른 오버헤드가 추가된다. 실제 영향은 AC07의 p95 및 성공 TPS로 검증한다.
- 본 결정은 설계 확정이며 구현·실행 결과를 의미하지 않는다.

## 기술면접·보고서 설명 근거
**왜 `AtomicBoolean` 하나로 충분하지 않은가?** 중복 캡처 권한뿐 아니라 요청이 종료 중인지와 캡처가 진행 중인지까지 표현해야 하기 때문이다.

**왜 캡처 전체를 잠그지 않는가?** 상대적으로 비용이 큰 스택 조회 동안 요청 종료 상태 잠금을 점유하지 않기 위해서다.

**캡처 중 종료되면?** 먼저 권한을 얻은 캡처의 결과 또는 실패 신호를 확인한 다음 Registry와 Thread 참조를 정리한다.

# ADR-029: 동시 발급 테스트의 재현성과 PostgreSQL 잠금 제한 검증

## 상태
Accepted

## 컨텍스트
ADR-008과 ADR-026은 재고 30개인 쿠폰에 서로 다른 사용자 100명이 동시 발급을 요청하면 정확히 30건이 성공해야 하는 AC01, 동일 사용자 20건의 동시 발급에서는 1건 성공·19건 중복 발급 오류가 발생해야 하는 AC02를 정했다. ADR-020은 PostgreSQL 행 잠금 획득 대기에 `lock_timeout='3s'`를 적용했다.

요청 작업의 동시 시작은 Executor 대기, HikariCP 커넥션 대기, PostgreSQL 트랜잭션 실행 및 행 잠금 대기와 서로 다른 단계다. 특히 PostgreSQL의 3초 잠금 제한은 전체 요청시간이나 커넥션 풀 대기시간을 제한하지 않는다. 실패 시 이 구간들을 혼동하면 비즈니스 정합성 결함과 환경·잠금 경합 문제를 구별하기 어렵다. 동시 실행 스케줄에 따른 재현성도 확인할 필요가 있다.

## 결정
1. **기존 AC01·AC02 통과 조건을 완화하지 않는다.** AC01은 서로 다른 문자열 `userId` 100개로 재고 30개를 요청하여 성공 30건, 최종 `issued_count=30`, 발급 이력 30건을 필수로 검증한다. 나머지 70건은 정의된 오류만 허용하고 잠금 시간 초과 503은 별도 집계한다. 성공이 30건 미만이면 실패한다. AC02는 동일 `userId`의 동시 요청 20건에서 성공 1건, 중복 발급 19건, `issued_count=1`, 발급 이력 1건을 필수로 검증한다. AC02의 잠금 시간 초과는 통과 조건 위반이다.
2. AC01은 **100개 작업**, AC02는 **20개 작업**을 준비하고, Executor 작업 스레드 수는 해당 시나리오의 요청 수와 같게 설정한다. 테스트 전용 **HikariCP 최대 커넥션 수의 초기 고정값은 32**로 둔다. 이는 비즈니스 요구사항이 아니라 재현 가능한 테스트 환경 설정이다. 실제 PostgreSQL 연결 한도 및 실행 환경을 점검하고, 변경 시 설정값·이유를 증거에 남긴다.
3. `CountDownLatch`로 모든 작업이 시작 지점에 도달했는지 확인한 다음 공통 시작 신호를 보낸다. 준비·완료 대기에 유한한 테스트 제한시간을 두고, Executor의 종료를 확인한다. 이 제한시간은 PostgreSQL `lock_timeout=3s`와 별개다. 시작 신호는 DB 연결이나 행 잠금의 완전한 동시 획득을 보장하지 않는다.
4. 실패는 **비즈니스 정합성 오류**, **PostgreSQL 잠금 경합·SQLSTATE `55P03`(HTTP 경로에서는 503)**, **실행 환경 오류(커넥션 획득 실패·Executor 종료 실패 등)**로 분류한다. Service 통합 테스트는 도메인 예외를 분류하고 HTTP 응답 코드 계약은 별도 HTTP 통합 테스트에서 검증한다. 실패 분류만으로 인수 조건 위반을 PASS로 변경하지 않는다. 잠금 제한으로 거부된 작업을 자동 재시도하여 성공 건수를 맞추지 않는다.
5. AC01과 AC02를 **각각 독립 Fixture로 3회 실행하고 세 번 모두 통과**해야 최종 PASS로 판정한다. 실패 실행은 덮어쓰거나 통과한 실행으로 대체하지 않는다. 3회 반복은 재현성의 추가 증거이지 모든 경쟁 스케줄에 대한 통계적 보장은 아니다.
6. 실행마다 실행 ID·Fixture ID, 작업·스레드·커넥션 풀 설정, 성공·중복·품절·잠금 시간 초과·기타 실패 건수, 최종 `issued_count`와 발급 이력 수, 실행 시각·소요시간, 예외 유형 및 발생 단계를 보존한다. 기존 ADR-013의 커밋된 독립 Fixture·자기 데이터만 정리 정책과 ADR-014·ADR-026의 증거 계약을 따른다.

## 근거
- **요청 동시성**과 **DB 연결 수**를 구분하여 테스트 조건을 명확하게 한다. 커넥션 100개를 사용하는 것만으로 정합성 검증이 강화되지는 않으며 연결 자원과 잠금 경합이 과도해질 수 있다.
- 고정된 초기 설정값과 구체적 실패 분류를 사용하면, 정합성 오류·DB 잠금 제한·테스트 환경 문제를 구별하여 분석할 수 있다.
- 반복마다 독립 Fixture를 사용하고 실제 PostgreSQL의 잠금·UNIQUE 제약·최종 DB 상태를 확인해 단일 실행의 우연한 통과에만 의존하지 않는다.
- 실패 시 자동 재시도를 하지 않아 기존 트랜잭션·무재시도 정책과 인수 조건의 의미를 보존한다.

## 대안 및 Trade-off
- **추천안 — 고정 환경(초기 커넥션 풀 32) + 실패 분류 + 독립 Fixture 3회:** 기존 통과 기준을 보존하면서 실행 조건과 문제 원인을 추적할 수 있다. 단점은 32개가 최적이라는 보장이 없고 증거 수집·테스트 제어 코드가 늘어난다는 점이다. 이를 설정값 기록, 커넥션 대기와 DB 잠금 대기 구분, 공통 Fixture·결과 분류기·DB Assertion 재사용으로 보완한다.
- **요청 수와 동일한 DB 커넥션 100개 확보:** DB 동시 진입을 확대할 수 있으나 연결 자원·잠금 경합·환경 영향이 증가한다. 동시 요청 100건의 검증과 DB 연결 100개 확보는 동일한 목표가 아니다.
- **아주 작은 커넥션 풀로 DB 작업 순차화:** 잠금 시간 초과 가능성을 줄일 수 있으나 실제 PostgreSQL 동시 경합 검증이 약해질 수 있다.
- **잠금 시간 초과 시 자동 재시도:** 최종 성공 건수는 맞추기 쉬우나 최초 동시 발급 시나리오와 ADR-020의 무재시도 정책이 바뀌므로 채택하지 않는다.
- **단 1회 실행:** 구현·실행 비용이 적지만 실행 순서 변화에 대한 재현 증거가 부족하다. 3회 반복 역시 모든 동시성 오류를 증명하지 못하므로 DB 상태 검증과 AC08·AC09의 통제된 실제 잠금 테스트를 병행한다.

## 테스트 검증 계약
- AC01: 매 실행마다 작업 100개·서로 다른 사용자 100명·재고 30, 성공 30건, DB 카운트 및 발급 이력 30건, 나머지 오류의 허용 여부와 503 별도 집계.
- AC02: 매 실행마다 작업 20개·동일 사용자, 성공 1건·중복 19건, DB 카운트 및 발급 이력 1건; 503 발생 시 실패.
- 각 작업이 공통 시작 신호에 도달했는지 검증하고 대기·종료 제한시간을 둔다. 종료 실패 및 연결 자원 오류는 숨기지 않는다.
- 테스트별 독립 Fixture를 사용하여 **각 시나리오 3회 모두 통과**해야 한다. 각 실행의 원본 결과를 보존한다.
- Service 통합 테스트의 도메인 예외와 별도 HTTP 통합 테스트의 409/503 응답을 혼동하지 않는다.

## 이전 ADR과의 관계 및 변경 사유
- **ADR-004, ADR-008, ADR-012, ADR-013, ADR-020, ADR-026을 대체하지 않는다.** 비관적 잠금, AC01·AC02 통과 기준, 테스트 계층·Fixture 정책, 3초 잠금 제한과 HTTP/DB 검증 조건을 유지한다.
- 기존 ADR에는 Executor 작업 수와 커넥션 수의 관계, 반복 실행 횟수, 동시 테스트 실패 분류가 충분히 정의되지 않았다. **ADR-029는 그 실행·재현성 계약만 새로 추가**한다.
- 이전 ADR의 원문과 상태를 수정하지 않는다. 향후 기존 결정을 실제로 변경하는 경우 새 ADR에서 변경 이유 및 대체 관계를 명시한다.

## 결과
- AC01·AC02 성공 조건을 변경하지 않은 채 고정된 초기 테스트 환경과 반복 검증·진단 기준을 확보한다.
- 초기 커넥션 풀 32개 설정은 실행 환경에서 검증해야 하며, 테스트 통과나 성능을 선험적으로 보장하지 않는다.
- 본 ADR은 설계 확정일 뿐 실제 테스트 구현·실행·PASS를 뜻하지 않는다.

## 기술면접·보고서 설명 근거
**왜 요청은 100개인데 커넥션은 32개인가?** 100개는 인수 조건의 요청 동시성이고, 32개는 테스트 환경에서 고정해 기록하는 DB 연결 자원 설정이기 때문이다. 두 수치는 같은 의미가 아니며 최종 PostgreSQL 상태로 정합성을 확인한다.

**커넥션 풀이 작으면 경쟁 문제가 감춰지지 않는가?** 가능성을 인정한다. 그래서 연결 대기와 DB 잠금 대기를 구별하고 AC08·AC09에서 통제된 행 잠금 대기를 별도로 재현한다.

**3회 통과하면 완전히 안전한가?** 아니다. 반복은 재현성 증거이며, 핵심 보장은 실제 트랜잭션 잠금·UNIQUE 제약 및 DB 최종 상태 검증을 통해 다각도로 확인한다.

# ADR-030: 10시간 구현 WBS 및 GitHub·ZIP 인도·검증 계약

## 상태
Accepted

## 컨텍스트
ADR-001~029의 설계와 테스트 계획을 실제 구현 순서, 시간 예산, 재현 가능한 인도물로 연결해야 한다. 공개 GitHub 저장소와 ZIP의 파일 트리를 일치시키고, 실제 실행하지 않은 검증을 통과로 표시하지 않아야 한다.

## 결정
승인된 WBS 초안의 600분 작업 분배, 완료 기준, 테스트 결과 표기, GitHub·ZIP 동일성, README 실행 계약을 채택한다. 세부 실행 계약은 아래에 보존한다.

## 결정 근거 및 대안·Trade-off
- **추천안(채택):** W1~W5의 의존성 순서로 600분을 배분하고, 실제 실행 로그를 남긴 뒤 특정 Git 커밋에서 ZIP을 생성한다. 재현성과 정직한 결과 공개가 가능하다. 단점은 AC07 최소 24분의 부하 구간과 환경 준비·검증이 시간 예산을 압박한다는 점이며, 미완료 항목을 `NOT_RUN`/`BLOCKED`로 명시하고 검증을 생략하여 PASS로 꾸미지 않는 방식으로 대응한다.
- **대안 1 — 소스만 먼저 ZIP으로 제공:** 전달은 빠르지만 빌드·테스트 상태와 재현성이 검증되지 않아 채택하지 않는다.
- **대안 2 — GitHub와 ZIP을 별도로 관리:** 배포가 유연하지만 소스 차이와 버전 혼동 위험이 커 채택하지 않는다.
- **대안 3 — 10시간에 맞춰 AC07 실행을 축소:** 시간 절감이 가능하지만 기존 ADR의 실험 조건을 훼손하므로 채택하지 않는다.

## 이전 ADR과의 관계 및 변경 사유
ADR-001~029의 기술·테스트 결정을 대체하거나 원문을 변경하지 않는다. 기존 ADR에서 정하지 않은 구현 일정, 검증 증거 및 인도 기준을 후속 결정으로 추가한다. 설계 동결은 별도 승인 사항이며 이 ADR의 채택만으로 구현 시작이나 실제 테스트 완료를 의미하지 않는다.

## 2. 테스트 실행·결과 기록 계약

구현 후 다음 명령을 **실제로 실행하고** 종료코드·명령·일시·환경·커밋·로그 위치를 `docs/evidence/test-results.txt`에 기록한다.

```bash
./gradlew clean build
make test-unit
make test-integration
make test-lock-wait
make test-overhead
make evidence
```

- `./gradlew clean build` 결과와 모든 `make` 명령의 성공 여부를 **개별 기록**한다. 명령이 제공되지 않거나 환경 문제로 실행 못 했으면 `NOT_RUN` 또는 `BLOCKED`로 기록한다.
- `docs/evidence/ac-results.md`에서 AC01~AC11 각각 `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`, `INVALID` 또는 `REVIEW_REQUIRED` 등 실측 상태를 정확히 표시한다. `INVALID`/`REVIEW_REQUIRED`는 성능 목표 PASS와 구별한다.
- **PASS 조건:** 실제 실행 + 해당 Assertion 충족 + 요구되는 원본 증거 확인. 테스트하지 않았거나 로그가 없으면 PASS가 아니다.
- **성능 비교:** 정상 커밋 쿠폰 발급 성공 TPS가 주 지표; HTTP 201 요청별 원본과 해당 실행 DB 발급 이력을 대조한다. p95는 성공 HTTP 201의 Nearest-Rank. 전체 HTTP RPS는 보조 지표. 60초 완료 경계 밖의 요청은 따로 보존한다.
- 테스트 실패를 숨기기 위해 임의로 성공 값·그래프를 생성하거나, 실패한 실행을 통과한 실행으로 덮어쓰지 않는다.

## 3. 공개 저장소와 ZIP의 동일성 계약

**동일성의 기준:** `GitHub 공개 저장소의 특정 태그/커밋에 추적되는 프로젝트 파일 트리 == 제공하는 ZIP 내부 프로젝트 파일 트리`. ZIP 자체의 파일명·압축 메타데이터가 아니라, 압축을 해제한 프로젝트 파일/내용을 비교한다.

ZIP 포함 대상:
- 전체 Java 소스 코드·Gradle Wrapper·`build.gradle`·`settings.gradle` 등 빌드 파일
- 단위·통합·HTTP 테스트 코드, Locust 부하 테스트 파일
- Docker Compose, 예시 환경 설정 `.env.example`, Makefile, 시딩/측정/분석/시각화 스크립트
- `README.md`, `docs/01-requirements.md`~`docs/07-decision-log.md`, ADR, `docs/test-reproduction.md`, 실제 생성된 증거와 결과 상태표

비포함 대상: 비밀키·실제 비밀번호를 포함한 `.env`, 로컬 DB 볼륨, `.git` 디렉터리, 개인 경로의 로그, 불필요한 Gradle 빌드 출력. 필요한 실행 설정은 예시 파일로 제공한다.

인도 절차:
1. 모든 코드·문서·검증 결과를 저장소에 **커밋**한다. 커밋 기준의 공개 GitHub 태그(예: `v0.1.0`)를 준비한다. GitHub에 실제 게시하지 못했으면 'GitHub 동기화 완료'라고 표기하지 않는다.
2. 소스 트리에서 위 명령으로 **빌드·테스트를 먼저 실행**하고 결과를 기록·커밋한다. 결과 기록 후 코드가 변경되면 **다시 검증**한다.
3. 동일 커밋에서 `git archive --format=zip --prefix=coupon-apm-lab/ -o coupon-apm-lab-<shortsha>.zip <commit-or-tag>`로 ZIP을 만든다. 태그가 가리키는 파일 목록/파일 해시와 압축 해제된 ZIP 트리를 비교한다.
4. GitHub URL·태그·커밋 SHA·ZIP SHA-256·파일 트리 검증 결과를 ZIP 외부 릴리스 기록에 남기고, ZIP의 README에서 사용자가 재현 절차를 찾을 수 있게 한다.

**중요:** 빌드·테스트 실행이 실패해도 요청 시 검토용 ZIP은 제공할 수 있으나 `검증 완료/전체 PASS`로 표시하지 않는다. 실패·미실행의 원인과 재현 명령을 함께 제공한다.

## 4. README 필수 실행 경로

README에는 Linux/WSL2를 기준으로 다음 순서와 실제 가능한 명령을 설명한다.

```bash
# 1. 사전 요구사항: JDK 21, Docker Compose, Python, Locust, Matplotlib, make
# 2. 실행 설정 복사 및 필요한 환경 값 지정 (예: .env.example)
# 3. PostgreSQL 시작
docker compose up -d db
# 4. 빌드·일반 테스트
./gradlew clean build
# 5. 구분된 검증 명령
make test-unit
make test-integration
make test-lock-wait
make test-overhead
make evidence
```

명령의 정확한 서비스명·설정 변수·옵션은 구현된 `compose.yaml`과 스크립트에 맞춰 최종 확정한다. 따라서 위 코드 블록은 **예정된 인터페이스**이며 현재 실행이 확인된 명령이 아니다. 수동 데이터 정리 명령은 `make clean-run RUN_ID=...` 형태로 별도 설명하되 기본 흐름에서 자동 호출하지 않는다.

# ADR-031: 구현 기준선 설계 동결 선언

## 상태
Accepted

## 컨텍스트
ADR-001~030에서 요구사항, PostgreSQL 기반 쿠폰 발급 정합성, 경량 APM, AC01~AC11 검증, 성능 실험, 10시간 WBS 및 GitHub·ZIP 인도 기준을 결정했다. ADR-030의 동결 체크 항목 중 남아 있던 사용자 승인 항목이 2026-11-08에 명시적으로 승인되었다. 구현 시작 시점에 적용할 기준선과 이후 변경 기록 원칙을 명확히 해야 한다.

## 결정
1. **ADR-001~030을 2026-11-08 기준 구현 설계 기준선으로 동결한다.** 본 ADR-031은 동결 승인 사실을 기록하며 기존 ADR 본문을 수정하지 않는다.
2. 이후 요구사항·아키텍처·검증 계약을 변경해야 한다면 기존 ADR을 덮어쓰지 않고 **새 ADR**에 변경 배경, 이전 결정과의 관계, 대안, Trade-off, 영향 범위를 기록하고 승인을 받는다. 단순 구현상 세부사항은 기존 동결 계약 범위 안에서 진행할 수 있다.
3. 구현 범위는 ADR-030의 **600분(10시간) WBS**를 따른다. 실제 소요시간을 기록하며 목표 시간과 실제 시간을 구분한다.
4. 최종 인도물은 전체 소스·테스트·스크립트·설정·문서가 포함된 ZIP이며, GitHub 공개 저장소와 동일 커밋을 기준으로 일치 여부를 검증한다. GitHub 게시가 확인되지 않으면 게시 완료로 표기하지 않는다.
5. ZIP 생성 전 실제 빌드·테스트를 실행하고 결과를 기록한다. 실행하지 않은 항목은 `NOT_RUN`, 환경상 실행할 수 없는 항목은 `BLOCKED` 등 사실에 맞는 상태로 기록하며 **검증하지 않은 결과를 PASS로 표시하지 않는다.**
6. **설계 동결은 구현 착수 또는 10시간 타이머 시작을 의미하지 않는다.** 구현 시작 시점을 별도로 기록한다.

## 결정 근거
동결 시점을 명시하면 구현 중 요구사항이 암묵적으로 바뀌는 일을 방지하고, 포트폴리오에서 최초 설계와 후속 변경을 구분해 설명할 수 있다. 실행 결과와 인도물의 검증 상태를 분리하면 재현 가능성과 신뢰성을 유지할 수 있다.

## 대안 및 Trade-off
| 대안 | 장점 | 단점 및 보완 |
|---|---|---|
| **A. 기준선 동결 + 변경 시 신규 ADR (채택)** | 의사결정 이력 보존, 구현 기준 명확 | 문서 작성 비용 증가; 변경 영향이 있는 경우에만 신규 ADR 작성 |
| B. 기존 ADR을 최신 상태로 덮어쓰기 | 현재 설계만 읽기 쉬움 | 결정 변경 이유와 시점이 사라짐 |
| C. 동결 없이 구현 진행 | 즉시 변경 가능 | 범위 증가와 검증 기준 변경을 추적하기 어려움 |

## 결과
설계 기준선 확정. **코드 구현, 실제 빌드·테스트, GitHub 게시 및 ZIP 생성은 아직 수행했다고 간주하지 않는다.** 구현 착수 후 실제 상태를 별도 기록한다.

## 기존 ADR과의 관계
ADR-001~029의 기술 결정 및 ADR-030의 WBS·인도 계약을 그대로 유지한다. 기존 ADR을 대체하지 않는 승인·기준선 기록이다.
